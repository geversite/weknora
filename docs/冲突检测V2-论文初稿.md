## 摘要

版本化知识库通常通过分块检索与 chunk-pair 级冲突检测维护内容一致性。然而，单个冲突对难以表达多个来源围绕同一事实的争议，也无法安全地将局部 A/B 方向直接转换为全局知识治理动作。本文提出 WeKnora Conflict Detection V2，一个面向版本化、多来源知识库的事实级冲突治理原型。系统首先从文档中抽取带原文证据的原子声明，并结合精确 claim key 与语义 fallback 构造候选；随后采用规则层与 grounded batch LLM 级联完成冲突裁决；最后将 raw chunk-pair conflicts 聚合为 DisputedFact，并在所有来源均具有显式且一致的发布机构、日期与版本证据时提出全局 winner proposal。为避免将局部方向误用为全局副作用，winner proposal 仅具建议性，实际 adoption 必须由显式、版本化快照触发；每次 adoption 会持久化成员与被禁用 chunk 的精确记录，随后可通过 reopen 操作可审计地恢复。

在真实 HTTP API、DocReader、Asynq、PostgreSQL 和配置模型组成的实验环境中，C2-B4 相对 C1 将 LLM 调用从 48 降至 9（降低 81.25%），Token 降低 41.50%，端到端检测时延降低 47.79%。受控 lifecycle matrix 在 5 个 policy cases 的 3 次 independent replicates 中完成 15/15 case executions、9/9 adoption-reopen cycles，且 15 个 detector artifacts 的 dead-letter count 均为零。进一步地，在 12 个 development 与 12 个 held-out synthetic fact families 上，系统完成了 binary DocReader integration 与事实家族级 policy evaluation；完整 holdout 的 36/36 executions 和 18/18 lifecycle cycles 均通过。与 latest-upload、date-only、version-only 和 raw C3 local vote 相比，C4.6 global proposal 在该构造 holdout 中获得 1.000 的事实家族 policy accuracy 且没有 unsafe action。本文的结论限定为受控系统与安全协议验证；真实业务文档泛化、复杂 authority hierarchy 与双审阅 human evaluation 仍留作后续工作。

**关键词：** 知识库治理；冲突检测；声明抽取；事实级聚类；版本化文档；可撤销决策；检索增强生成

## Abstract

Versioned knowledge bases are commonly maintained through chunk retrieval and chunk-pair conflict detection. However, an individual pair cannot naturally represent a dispute shared by multiple sources, nor can its local A/B direction be safely promoted to a global governance action. We present WeKnora Conflict Detection V2, a fact-level conflict-governance prototype for versioned, multi-source knowledge bases. The system extracts atomic claims with source quotes, combines exact claim keys with semantic fallback candidates, and applies a rule-plus-grounded-LLM cascade for conflict adjudication. Raw chunk-pair conflicts are then projected into DisputedFacts. A global winner proposal is produced only when every source carries explicit, mutually consistent issuer, date, and version evidence. To prevent local pair directions from causing unsafe global effects, proposals are advisory; adoption requires an explicit snapshot-bound request, and every adoption is durably recorded so that a precise reopen operation can restore only the recorded loser chunks.

In a live environment using HTTP APIs, DocReader, Asynq, PostgreSQL, and configured models, C2-B4 reduced LLM calls from 48 to 9 relative to C1, with 41.50% fewer tokens and 47.79% lower detection latency. A controlled lifecycle matrix completed 15/15 independent case executions and 9/9 adopt-reopen cycles with zero dead letters across 15 detector artifacts. In an expanded synthetic development/holdout policy corpus, the held-out matrix completed 36/36 executions and 18/18 lifecycle cycles. At the fact-family level, the global proposal policy achieved 1.000 controlled accuracy with zero unsafe actions, whereas latest-upload, date-only, version-only, and raw local-vote baselines produced unsafe proposals. These findings establish controlled integration and safety evidence rather than real-document generalization, human-review accuracy, or seed-controlled causal claims.

**Keywords:** knowledge-base governance; conflict detection; claim extraction; fact clustering; versioned documents; reversible decisions

# 1 引言

大型知识库中的内容更新通常以“上传一份新文档”或“修改若干分块”的形式发生。对于同一业务规则、操作标准或制度条款，多个来源可能分别提供不同数值、日期、状态或适用范围。现有知识库系统大多以检索相关性为中心：当多个来源表达不一致时，系统可能同时召回它们，也可能依赖时间、上传顺序或局部相似度隐式偏向其中一方。该行为至少存在两个问题。

第一，chunk-pair 级冲突并不是用户真正需要裁决的单位。同一事实在三份文档中分别出现时，系统可能生成多个两两 raw conflicts；人工看到的是多条重复告警，而不是“一项事实存在多个候选值”的结构化争议。第二，局部 chunk A 与 B 的“较新/较旧”关系不等于全局 winner。例如，三份来源中可能出现不同发布机构、日期与版本号方向相反、日期区间重叠或版本并列。若系统将一条 raw pair 的方向直接传播为禁用其他来源的动作，便可能产生不可逆或错误的知识治理副作用。

本文关注的不是自动替代人类的权威判断，而是构造一个安全、可审计、可撤销的事实级冲突治理协议。我们提出 WeKnora Conflict Detection V2：从可验证的原子声明出发，先降低候选与裁决成本，再将 raw conflicts 聚为 DisputedFact；对于符合严格 metadata 条件的争议，仅产生 advisory winner proposal。真正影响检索可见性的 adoption 必须由显式请求触发，且携带 proposal snapshot；若发现判断不再适用，则 reopen 只能恢复该次 durable adoption 记录中精确列出的 targets。

本文贡献如下：

1. **声明级候选与级联裁决。** 我们在知识摄取链路中抽取 `Claim=(subject, predicate, value, qualifiers, quote)`，以 claim key 为主候选通道，并在未覆盖时保留 HybridSearch fallback；规则层优先处理可安全判定的情况，灰区交由 grounded batch LLM。
2. **事实级聚类。** 我们将 raw chunk-pair conflicts 投影为以 claim key 或保守 fallback anchor 标识的 DisputedFact，从而将多个重复冲突转化为一个多来源、候选值可见的裁决单位。
3. **全局 proposal 与显式可撤销生命周期。** C4.6 在所有 cluster sources 上检查 issuer、date 和 version 的一致性与唯一严格最大值；C4.7 以 snapshot-bound adoption 执行全局 side effect；C4.8 以 durable record 支持 precise reopen。
4. **可复现实验链路。** 我们通过真实 HTTP、DocReader、Asynq、PostgreSQL 与配置模型运行 C1–C4.10；报告 C2 成本消融、C4 lifecycle matrix、binary file integration，以及 development/holdout synthetic policy baseline 对照。

本文其余部分组织如下：第 2 节定义问题与安全不变量；第 3 节介绍系统方法；第 4 节说明实现；第 5 节报告实验；第 6 节讨论威胁与限制；第 7 节给出相关工作框架；第 8 节总结全文。

# 2 问题定义与安全不变量

## 2.1 声明、冲突与争议事实

对于文档分块 $x$，系统抽取一组原子声明：

$$
c=(s,p,v,q,e),
$$

其中 $s$ 是主体，$p$ 是稳定属性，$v$ 是取值，$q$ 是限定词，$e$ 是可回溯至原文的短引用。系统将归一化后的 $(s,p)$ 表示为：

$$
key(c)=\mathrm{normalize}(s,p).
$$

一个 raw conflict $r_{ij}$ 对应两个不同来源的分块或声明证据。它仍是检测系统的底层输出单位，但不应直接等价于用户的最终裁决单位。对于具有相同精确 claim key 的 raw conflicts，或满足保守 fallback anchor 条件的 raw conflicts，系统构造：

$$
f=(k,S,V,R),
$$

其中 $k$ 是事实锚点，$S$ 是来源集合，$V$ 是候选值集合，$R$ 是 raw conflict 成员集合。$f$ 即 DisputedFact。

## 2.2 Winner proposal 的条件

每个来源文档 $d\in S$ 的 metadata snapshot 表示为：

$$
m(d)=(issuer(d),date(d),version(d)).
$$

系统只在以下条件全部成立时，对候选来源 $d^*$ 提出 global winner proposal：

1. 每个来源均具有可解析的 metadata snapshot；
2. 所有来源的归一化 issuer 相同；
3. 每个 date / version 信号可比较，且两个信号存在时方向一致；
4. $d^*$ 相对于任一其他来源均严格较新；
5. 满足上述条件的候选恰有一个。

即：

$$
\exists!d^*\in S,\ \forall d\in S\setminus\{d^*\}:d^*\succ d.
$$

当 metadata 缺失、issuer 不同、日期区间重叠、版本并列或日期与版本方向不一致时，系统 abstain，不产生 proposal。

## 2.3 显式 adoption 与 reopen

proposal 本身不改变 raw conflict 状态，也不禁用任何 chunk。adoption 请求必须显式携带：

```text
DisputedFact ID
expected winner knowledge ID
proposal version
proposal updated_at snapshot
proposal source count
可选审计说明
```

后端在同一事务中重新验证 proposal、member topology、chunk ownership 与 enabled state。只有所有条件仍满足时，才将 raw members 标记为 `resolved_global_winner`，保留 winner chunks，并禁用 non-winner source chunks。

每次成功 adoption 都写入 durable record，至少记录：

```text
member conflict IDs
disabled chunk IDs
disabled knowledge IDs
winner knowledge ID
proposal snapshot
adopted / revoked 状态与审计时间
```

reopen 同样要求显式 durable adoption ID 和 DisputedFact snapshot。它只恢复该 durable record 精确记录、且当前仍满足 ownership/state 条件的 targets；若 cluster 已变化、snapshot stale、target 被其他 active adoption 占用或不存在 active adoption，则返回 HTTP 409，不产生部分恢复。

# 3 系统方法

## 3.1 C1：声明抽取与双通道候选

文档完成基础解析后，系统以异步任务抽取声明。每条声明保留主体、属性、取值、限定词、值类型和原文 quote。为了减少跨文档表述差异导致的遗漏，候选生成包含两条通道：

```text
精确通道：同 claim_key 的声明直接配对
fallback 通道：任一声明未获得有效精确 counterpart 的 chunk 保留 HybridSearch 语义候选
```

这一覆盖策略避免“某个 chunk 含一条精确命中声明后，其余未匹配声明被错误视为已覆盖”的漏检。claim extraction 成功后才触发 conflict detection，保证 `claim:extract → conflict:detect` 的时序屏障。

## 3.2 C2：规则与 grounded LLM cascade

C2 将候选裁决划分为三类：

```text
no_conflict
直接 fact_contradiction
needs_llm
```

例如，同一精确 claim key、单位兼容、限定词等价且数值不同的情形可由规则直接判为 `fact_contradiction`；日期/version、文本枚举、限定词不等或语义 fallback 情形进入 LLM。C2-B4 将若干候选打包，要求模型输出结构化结果与连续原文 evidence quotes；positive quote 无法在原分块中定位时会重试或退回单对 verifier。该设计将“模型给出结论”限制为带 source-grounded evidence 的可审计输出。

## 3.3 C4：从 raw conflicts 到 DisputedFact

每个最终 raw conflict 在持久化前获得事实锚点：

```text
claim_key
fuzzy_slot
document_singleton
chunk_pair
```

精确 claim key 优先；fallback anchor 仅在 post-verdict、证据充足时使用。系统刻意不将 schema drift 或无 provenance 的历史 raw rows 激进合并。聚类以 `(tenant, KB, fact_key)` 为单位幂等 upsert DisputedFact，并同步维护来源数、候选值、pending conflict 数与 member cluster ID。

## 3.4 C3/C4.6：从局部 metadata 到全局 proposal

C3 首先对 raw pair 解析显式 title/header metadata，并给出 advisory `resolved_newer_wins` 或 `resolved_older_wins` suggestion。C4.6 不把这些 pair-level suggestion 直接当作 winner 指令，而是在 cluster 全体来源上重新检查唯一严格最大来源。该区别避免以下错误：

```text
局部 A↔B 中 A 较新
≠
在 A、B、C 三个来源中 A 是全局 winner
```

## 3.5 C4.7/C4.8：可审计治理生命周期

C4.7 的 adoption 以当前 proposal snapshot 为前提；C4.8 的 reopen 以当前 active durable adoption 为前提。二者均在事务中锁定 DisputedFact、raw members 和 target chunks，并使用 HTTP 409 表示 stale/no-proposal/no-active-adoption/partial-state 等 fail-closed 条件。

该协议的目标不是“自动清理旧文档”，而是将一次经过人工确认的全局选择转化为可恢复的检索可见性状态。

# 4 实现

原型构建在 WeKnora 后端之上，使用 Go 服务、PostgreSQL、Redis/Asynq、DocReader 与既有知识库 API。实现新增或扩展了如下持久化对象：

| 对象 | 作用 |
|---|---|
| `claims` | 存储声明及其 source span、claim key、value normalization 与抽取版本 |
| `conflict_detection_runs` | 存储 C2 候选、规则、LLM、Token、时延与完成状态 |
| `disputed_facts` | 存储事实锚点、成员聚合、候选值、来源与 proposal |
| `disputed_fact_winner_proposals` 相关字段 | 存储 C4.6 advisory global winner 信息 |
| `disputed_fact_winner_adoptions` | 存储 C4.7 adoption 与 C4.8 revoke/reopen 所需 durable evidence |

系统暴露以下无 UI 的研究 API：

```text
POST /knowledge-bases/:id/conflicts/clusters/rebuild
POST /knowledge-bases/:id/conflicts/clusters/resolve
POST /knowledge-bases/:id/conflicts/clusters/adopt-winner
POST /knowledge-bases/:id/conflicts/clusters/reopen-winner
```

实验脚本只通过 public HTTP API 创建 temporary KB、上传 Markdown 或 selected binary files、等待 Asynq、并以只读 PostgreSQL 导出 artifacts。实验脚本不直接向 `claims`、`knowledge_conflicts` 或 `disputed_facts` 插入数据。

# 5 实验

## 5.1 实验问题

本文回答四个问题：

```text
RQ1：claim-aware candidate channel 与 fallback 是否可在真实服务中运行并提供可审计声明证据？
RQ2：C2 cascade 能否在不损失场景完整性的前提下降低 LLM 调用成本？
RQ3：C4.6/C4.7/C4.8 能否在多来源 winner 与 fail-closed 条件下完成可重复生命周期？
RQ4：在构造的 fact-family holdout 中，global all-source proposal 是否比简单局部/单信号 baseline 更安全？
```

## 5.2 C1：声明抽取审计

C1 development/calibration audit 的 broad-maintenance gold-v2 candidate 结果为：

| Scope | Precision | Recall | 备注 |
|---|---:|---:|---|
| broad-maintenance | 0.867647 | 0.842857 | 人工审计修订口径；development/calibration |
| narrow conflict-critical | — | 1.000000（15/15） | 仅冲突关键事实；未单独估计 precision |

这些结果用于说明声明抽取与关键冲突覆盖的开发阶段表现。由于语料为 calibration corpus，且人工审计并非完整双审阅，本文不将其作为最终真实泛化指标。

## 5.3 C2：成本消融

在相同的 C1 full scenario 上，C2-B4 与 C1 的真实服务消融结果如下。

| Variant | Candidates | LLM calls | Tokens | Duration | Scenario integrity |
|---|---:|---:|---:|---:|---|
| C1 | 48 | 48 | 48,762 | 145,154 ms | PASS |
| C2-Rules | 48 | 47 | 47,293 | 149,111 ms | PASS |
| C2-B4 | 48 | 9 batch + 0 single | 28,528 | 75,789 ms | PASS |

相对 C1，C2-B4 将 LLM 调用从 48 降至 9（81.25% reduction；5.33× fewer），Token 降低 41.50%，检测时延降低 47.79%。这些数字表明规则筛选与 grounded batch adjudication 在该测试场景中能够降低成本。它们不等价于任意真实业务语料上的平均模型成本。

## 5.4 C4：事实级聚类

C4-Lite 的真实服务验证包括：

```text
三来源三取值：3 raw conflicts → 1 DisputedFact
schema-drift fallback：2 raw conflicts → 1 DisputedFact
```

这说明在证据满足精确或保守 fallback anchor 条件时，系统能以事实级而非 raw chunk-pair 级呈现争议。该结果是“裁决单位压缩”的工程证据，不直接等价于真实人工时间节省。

## 5.5 C4.9：lifecycle independent replicate matrix

C4.9 默认 matrix 使用 5 个 controlled policy cases、每个 3 次 independent replicates：

```text
case executions: 15/15
proposal TP / TN / FP / FN: 6 / 9 / 0 / 0
controlled precision / recall: 1.000 / 1.000
adopt → reopen cycles: 9/9
detector artifacts with dead_letter_count=0: 15/15
```

ordered 与 out-of-order triplet 均得到预期 global winner；cross issuer、date/version direction disagreement 和 metadata tie 均拒绝 proposal，且 adoption/reopen API 返回 fail-closed HTTP 409/no mutation。raw conflict 数在 1–3 间变化，平均为 1.866667；该波动进一步支持以 DisputedFact 而非 raw row 作为主要分析单位。

## 5.6 C4.10：binary file integration 与扩展 synthetic holdout

首先，binary DocReader fixture 验证了：

```text
DOCX lifecycle fixture: 4 cases × 3 replicates = 12/12
DOCX lifecycle cycles: 3/3
PDF ingress/claim smoke: claims=1
```

随后，确定性生成 24 个 synthetic fact families：12 个 development、12 个 holdout。development R=1 的 12/12 cases 仅用于收口 generator、metadata policy 和 scorer；在冻结后，holdout 使用 3 independent replicates。

完整 holdout：

| 项目 | 结果 |
|---|---:|
| Fact families | 12 |
| Replicates | 3 |
| Case executions | 36/36 |
| Positive / no-proposal executions | 18 / 18 |
| Lifecycle cycles | 18/18 |
| Dead-letter observations / total | 36 / 0 |
| Raw conflicts / DisputedFacts | 84 / 36 |
| Raw conflicts per DisputedFact | 2.333333 |
| Fact-family prediction stability | 12/12 |

事实家族主口径要求同一 family 的全部三次 replicate 都正确，结果如下：

| Method | TP | TN | FP | FN | Precision | Recall | Policy accuracy | Unsafe actions |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| C4.6 global proposal | 6 | 6 | 0 | 0 | 1.000 | 1.000 | 1.000 | 0 |
| Latest upload | 2 | 0 | 10 | 4 | 0.167 | 0.333 | 0.167 | 6 |
| Date only | 5 | 3 | 3 | 1 | 0.625 | 0.833 | 0.667 | 3 |
| Version only | 5 | 3 | 3 | 1 | 0.625 | 0.833 | 0.667 | 3 |
| Raw C3 local vote | 6 | 4 | 2 | 0 | 0.750 | 1.000 | 0.833 | 2 |

latest-upload 在乱序正例与全部 no-proposal 负例中表现不安全。date-only 与 version-only 在忽略 issuer 或另一种 metadata signal 时产生错误 proposal。raw C3 local vote 保持局部 pair direction，但在 mixed issuer 与 metadata missing topology 中无法保证 cluster 全来源一致。C4.6 的 all-source rule 在本构造 policy corpus 中避免了这些 unsafe actions。

需要强调的是：该结果来自有意设计的 metadata failure modes；它验证协议在这些条件下的行为，不表示现实业务文档中一定获得相同数值。

# 6 讨论与威胁

## 6.1 为什么 global proposal 不是自动裁决

global proposal 仅是对严格 metadata 条件的解释结果。现实组织中可能存在发布机构层级、地域适用范围、法律效力、内部草案与正式发文等未被当前原型建模的因素。因此，即使 proposal 存在，系统仍要求人工或上层工作流显式调用 adoption。该决策使“模型或规则的判断错误”不会自动转换为全局检索副作用。

## 6.2 Synthetic holdout 的有效性边界

本文的 extended synthetic corpus 具备明确 split、独立运行、source SHA-256、artifact 完整性和 baseline 对照。它可以验证：

```text
policy topology
metadata consistency conditions
proposal abstention
lifecycle side effects
baseline unsafe-action differences
```

但 synthetic documents 的句法简单、事实单一、metadata 完整可控，不能代表：

```text
真实长文档
扫描件/OCR
复杂表格
跨格式抽取 drift
事实粒度不一致
组织 authority hierarchy
真实用户编辑流程
```

## 6.3 模型与可重复性

实验使用 configured provider/model，但没有可移植的 provider RNG seed 控制。因此本文使用 independent replicate，而非 multi-seed causal experiment。我们报告 raw conflict 波动、per-family strict replicate policy 与 dead-letter integrity，而不把 3 次运行误称为 3 个独立事实样本。

## 6.4 Human evaluation 与真实语料

C1 的人工审计以 development/calibration 为主，C4.10 的 holdout 为 synthetic policy corpus。若未来需要主张真实业务文档效果，必须增加：

```text
有许可或匿名化的真实 fact families
严格 development/validation/holdout 隔离
```

# 8 结论

本文提出 WeKnora Conflict Detection V2，一个将知识库冲突从 raw chunk-pair 提升为事实级 DisputedFact 的研究原型。系统通过 claim-aware candidate cascade 降低检测成本，通过全来源 metadata consistency 提出 advisory global winner，并通过 explicit adoption 与 durable reopen 将知识治理副作用限制为可验证、可撤销的操作。

受控真实服务实验表明，该原型能够在 HTTP、DocReader、Asynq、PostgreSQL 与配置模型的完整链路中运行。C2-B4 在既有成本消融中显著减少 LLM 调用；C4.9 完成 15/15 lifecycle replicate executions 且 dead letters 为零；C4.10 binary fixture 与扩展 synthetic development/holdout 进一步验证了文件入口、全局 proposal、fail-closed abstention、adoption/reopen 和 baseline unsafe-action 差异。

本文的主要结论限定为：**事实级冲突治理原型可以在明确 metadata 条件下安全地聚合、proposal、adopt 与 reopen。** 未来工作将引入有许可的真实版本化语料、双审阅标注、复杂 authority semantics、跨格式文本 drift 评估以及更丰富的检索层治理策略。
