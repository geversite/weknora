## 1. 结论

C4.6 已在真实服务中完成 C3 的**逐 raw chunk-pair 版本建议**到 C4 的**事实级唯一全局胜方 proposal** 的保守聚合：

```text
同一 DisputedFact 的全部 raw member
→ 读取 detection-time doc_meta_a / doc_meta_b snapshot
→ 收集每个 source 的 issuer / 生效日期 / version
→ 一致性与可比性检查
→ 求唯一严格最大来源
→ 写入 DisputedFact advisory winner proposal
```

真实正、负例均以 exit code `0` 通过：

| 场景 | 输入 | 事实聚类 | proposal | 结果 |
|---|---|---:|---:|---|
| 同 issuer 三来源 | 天穹财团 V1 / V2 / V3；日期和版本严格递增 | 1 | 1 | `c46_v3` 通过唯一胜方断言，confidence ≥ 0.95 |
| 跨 issuer 负例 | 天穹财团 V1 vs 新弦工业 V3 | 1 | 0 | 即使日期/版本可比，也不建议任何 winner |

这证明 C4.6 没有把任意一条 raw A/B `resolved_newer_wins` 当作 cluster 级行动指令；它在全部来源上求唯一最大值。正例有 4 条 raw conflicts、4 条 C3 local suggestions，但最终只生成 **1** 条事实级 proposal，避免将 chunk-pair 重复误当成多个独立裁决。

导出的真实 PostgreSQL artifact 进一步确认了无副作用边界：正例的 4 条 raw member 和负例的 1 条 raw member 都保持 `status=pending`、`auto_resolved=false`；两个 run 的 `dead_letter_count` 都是 `0`。C4.6 仍是纯 advisory：它只写 `disputed_facts` 的 proposal 字段；不调用 Resolve、不禁用 chunk，也没有 proposal adoption API。C4.5 仍明确拒绝 `resolved_newer_wins` 和 `resolved_older_wins` 的 cluster 级传播。

## 2. 设计与安全边界

### 2.1 唯一全局最大值算法

输入是一个 `DisputedFact` 的全部 member `knowledge_conflicts`，而不是单行的 C3 suggestion。任一条件不满足即返回空 proposal：

```text
任一 source 缺失 metadata snapshot                    → 无 proposal
同一 source 在不同 member 中 metadata 自相矛盾         → 无 proposal
issuer 缺失或规范化后不完全一致                         → 无 proposal
任意 source pair 的日期 / version 不可比较             → 无 proposal
date 与 version 的方向不一致                            → 无 proposal
没有或不止一个“严格晚于所有其他 source”的候选           → 无 proposal
```

只有唯一候选对其他每个来源都严格较新，才生成 proposal。日期遵循 C3 的区间语义：`YYYY`、`YYYY-MM`、`YYYY-MM-DD` 的区间重叠即不可比较；有日期和 version 时二者方向必须一致。

### 2.2 持久化

PostgreSQL migration `000091_disputed_fact_winner_proposals` 与 SQLite 对齐 migration `000012` 新增：

```text
suggested_winner_knowledge_id
winner_proposal_reason
winner_proposal_confidence
winner_proposal_version
winner_proposal_source_count
```

`ConflictClustererVersion` 升级为 `c4-v6`，proposal version 固定为 `c3-c4-v1`。实验 runner 会在真正发起 HTTP 实验前检查全部五个列；`669c0a2` 补齐了遗漏的 Python readiness helper，因此 schema 缺失会显示为明确 migration 错误，而不是运行期 `NameError`。

### 2.3 无副作用约束

`Rebuild` 对 proposal 的写入目标只有 aggregate `DisputedFact`。proposal 不是 resolution：

```text
raw knowledge_conflicts.status       不由 proposal 改写
raw knowledge_conflicts.auto_resolved 不由 proposal 改写
chunk enable / penalty               不由 proposal 改写
C4.5 Resolve                         不由 proposal 调用
wiki / agent 写回                    不发生
```

因此 C4.6 的真实运行验证的是“建议正确产生/正确拒绝”，而不是尚未实现的 winner propagation。任何后续采纳必须由用户/API 显式触发，并在事务中重新校验 proposal 与 cluster 状态。

## 3. 真实运行证据

### 3.1 同发布机构三来源正例

```text
run: 20260901T130050Z-c46_global_winner_triplet-c2-rules-669c0a27
KB:  c3e3a888-3dc3-4d67-8780-16984ace96f4
```

输入文档均为同一事实“国内出差餐费补贴每日标准”，但带有 title 中的显式 metadata：

| 文档 | 发布机构 | 生效日期 | 版本 | 事实值 |
|---|---|---|---|---:|
| `c46_v1` | 天穹财团 | 2148-01-01 | V1.0 | 100 元 |
| `c46_v2` | 天穹财团 | 2148-06-01 | V2.0 | 150 元 |
| `c46_v3` | 天穹财团 | 2149-01-01 | V3.0 | 200 元 |

场景声明并由 runner 的 exit `0` 验证：

```text
C46_V2_V1 / C46_V3_V1 / C46_V3_V2 三个文档对均命中
expected_disputed_fact_count = 1
expected_disputed_fact_anchor_kinds = {claim_key: 1}
expected_disputed_fact_winner_count = 1
C46_PROPOSE_V3：winner_document = c46_v3，confidence >= 0.95
```

服务级汇总：

```text
claims：4
raw conflicts：4
disputed facts：1
raw conflicts / disputed fact：4.000
C2 rules(no/direct/LLM)：0 / 3 / 1
C2 LLM(batch/single)：0 / 1
C3 local suggestions：4（均为 resolved_newer_wins）
C3/C4.6 winner proposals：1
experiment exit code：0
```

最小文档对组合是三组；实际保留 4 条 raw row 是 chunk-pair 粒度检测的自然结果。C4.6 不依赖这一 raw row 数量，而是在 `claim_key` 事实锚点下将其归为一个 `DisputedFact`，再对三份 source metadata 求唯一最大值。

artifact 中的 aggregate 与 proposal：

```text
DisputedFact ID：7095d3a1-3c54-4b23-8a49-4b204c1c4618
clusterer_version：c4-v6
fact_key：claim_key:国内出差餐费补贴每日标准
source_count：3
candidate_values：[100 元, 150 元, 200 元]
pending_conflict_count：4
review_units_saved：3
winner_document：c46_v3
winner_proposal_confidence：0.99
winner_proposal_version：c3-c4-v1
winner_proposal_source_count：3
dead_letter_count：0
```

`winner_proposal_reason` 明确记录“同发布机构天穹财团”“在 3 个来源中”“仅 proposal，不自动裁决”。4 条 member 均绑定到该 DisputedFact，且实测均为：

```text
status = pending
auto_resolved = false
suggested_resolution = resolved_newer_wins
suggestion_confidence = 0.99
```

其中 `c46_v2 ↔ c46_v1` 有两条 raw chunk-pair rows，C2 type 分别为 `fact_contradiction` 与
`version_update`；另外两条为 `c46_v3 ↔ c46_v1`、`c46_v3 ↔ c46_v2` 的
`fact_contradiction`。C4.6 的 winner 计算不依赖这类 C2 type 或局部 A/B 方向。

## 4. 可重复实验与产物

```bash
make experiment-check
make experiment-c46
make experiment-c46-negative
```

每个 run 都以 public HTTP API 创建临时 KB、上传 manual documents、等待真实 Asynq detector tasks，并通过只读 PostgreSQL 导出证据。runner 不直接插入或修改 `claims`、`knowledge_conflicts`、`disputed_facts`。

关键产物：

```text
conflicts.json
conflict_document_pairs.json
disputed_facts.json
cluster_rebuild.json
cluster_metrics.json
winner_proposals.json
metrics.json
dead_letters.json
report.md
```

其中 `metrics.json` 对 C4.6 的硬断言包含：expected/observed proposal count、缺失的 expected winner、事实 cluster count 和 anchor kind；任何断言失败均返回 exit code `2`，而不是把不完整结果记作成功。

