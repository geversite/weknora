# C2 技术设计：声明级级联验证与批量裁决

> 所属系列：[冲突检测 V2 里程碑规划](冲突检测V2-里程碑规划.md)
>
> 状态：**C2-Lite 研究原型已冻结**。最终运行评估见
> [C2 生产运行与消融报告](冲突检测V2-C2-生产运行评估报告.md)。
>

> 最终 detector version：`c2-v4`；成本观测迁移：PostgreSQL `000086` / SQLite `000007`。

---

## 1. 目标与边界

C1 已将“是否值得比较”的问题从纯 chunk 相似度扩展为 claim-key 主通道加
HybridSearch fallback，但剩余候选仍需要语义裁决。C2-Lite 的目标是：

```text
保留 C1 的召回路径
→ 用极保守的确定性规则消除明确情况
→ 将灰区打包交给 LLM
→ 对 batch 正例施加原文证据约束
→ 持久化候选、规则、调用、token、延迟指标
```

C2-Lite 不是端到端产品化，也不试图在本期完成下列工作：

- 不部署 NLI / cross-encoder 服务；NLI 为以后可选层；
- 不用文档元数据自动裁决 `version_update`（C3）；
- 不聚类 `knowledge_conflicts` 的 chunk-pair 重复行（C4）；
- 不做批量 verdict 的长期全文审计表或前端设置页；
- 不把 claim extraction 的模型调用成本混入本页的冲突检测 LLM 成本。

所有 C2 模式均为 **KB 级 research configuration**，默认 / 未识别配置安全回退到
legacy C1 行为。

## 2. 模式与总流程

`types.IndexingStrategy` 新增 `conflict_cascade_mode`：

| Mode | claim extraction | 验证路径 |
|---|---:|---|
| `legacy` | 可开/关 | C1 每 candidate 单对 LLM 裁决 |
| `rules` | 开 | C2-A 规则 → 未决项 C1 单对 LLM |
| `rules_batch` | 开 | C2-A 规则 → 未决项 C2-B batch LLM |

实验 runner 对 variant 的固定映射：

```text
v1        claim_extract_enabled=false, conflict_cascade_mode=legacy
c1        claim_extract_enabled=true,  conflict_cascade_mode=legacy
c2-rules  claim_extract_enabled=true,  conflict_cascade_mode=rules
c2-batch  claim_extract_enabled=true,  conflict_cascade_mode=rules_batch
```

运行时链路：

```text
文档解析完成
  → claim:extract（C1；claims 完成持久化）
  → conflict:detect
      ├─ exact claim_key 候选
      ├─ 未被 exact 覆盖的 chunk → HybridSearch fallback 候选
      ├─ 同 chunk-pair 内存去重
      ├─ pending conflict 去重
      └─ fineAdjudicate
           ├─ legacy: 单对 LLM
           └─ C2:
                ├─ 规则 no_conflict → 丢弃
                ├─ 规则 direct_conflict → 直接形成 conflictPair
                └─ needs_llm
                     ├─ rules: 单对 LLM
                     └─ rules_batch: K=8 batch LLM
  → knowledge_conflicts（仍为 raw chunk-pair 行）
  → conflict_detection_runs（一次 detect task 一行）
```

C2 不修改 C1 的候选召回策略。特别是 schema drift（例如“测试时间”与“计划开始时间”）
仍可由 fallback 到达裁决层，而不是被严格 claim-key 条件提前丢弃。

## 3. C2-A：保守确定性规则

实现：`internal/application/service/conflict_rules.go`。

规则只对带有 **exact `ClaimKeyHit`** 的候选生效；任何 fallback 候选都保持
`needs_llm`。这是为了不把 C1 的同义词、主体边界和 schema drift 召回换成不安全的
便宜判定。

| 条件 | 动作 | 备注 |
|---|---|---|
| 同一 claim-key，`value_norm` 相同 | `no_conflict` | 同值不是值冲突 |
| 两侧均为 number；单位相同；qualifiers 完全相同；数值不同 | `direct_conflict` / `fact_contradiction` | 不调用 LLM |
| 明确互斥 scope（国内/国际、工作日/节假日），其余 qualifiers 相同 | `no_conflict` | 极小白名单 |
| date/version、text/enum、单位不兼容、qualifier 不同或未知 | `needs_llm` | 不用规则猜语义 |
| semantic fallback | `needs_llm` | 无例外 |

规则是 all-or-nothing 的 chunk-pair 判定：一个 pair 内若仍有不确定的声明关系，即不因
另一个同值声明而整个 pair 被提前丢弃。规则直判结果保留带 `[rule:...]` 的原因文本。

## 4. C2-B：批量 LLM 裁决

实现：`internal/application/service/conflict_batch.go`。

### 4.1 批量协议

```text
batch size       = 8
max completion   = 2200 tokens
batch retry      = 1
response format  = {"results":[...]} 或 bare array
```

每次 provider 调用只处理一个 `conflict:detect` task 内的一批候选，因此全库 aggregate
中 batch call 数不等于 `ceil(总候选/8)`；必须按每个新文档 task 的分组边界计算。

响应必须恰好包含 batch 中每个 `pair-000`…ID 一次。缺 ID、重复 ID、非 JSON 或部分
响应没有可信的 item 边界，会触发整个 batch 的 C1 单对 fallback。

### 4.2 Closed-world + proof-carrying 正例

早期 batch 实验曾把“文档未提及某事实”误判为隐含否定，也会将风险记录与防护措施、
建议与计划、不同时间阶段混作冲突。最终 prompt 明确规定：

```text
候选只是检索相关，不预设矛盾；
每个 id 独立判断，不得借用其他 id、标题、常识或价值推断；
沉默 / 未提及不是否定；
只有两侧都明确陈述同一主体、同一事实维度、兼容 scope 的互斥原子事实才可为 true。
```

任何 `conflict=true` 必须返回：

```json
{
  "id": "pair-000",
  "conflict": true,
  "type": "fact_contradiction",
  "reason": "中文一句话",
  "evidence_a": "片段 A 的连续原文短引",
  "evidence_b": "片段 B 的连续原文短引"
}
```

后端对 A/B 引文执行 NFKC、空白和标点宽松归一后，要求其分别出现在对应源 chunk 中，
且归一后长度为 6–160 runes。该校验是 grounding guard，不试图用字符串匹配自行判断
事实是否互斥。

### 4.3 失败隔离

C2-B 有两种不同的失败恢复路径：

| 情况 | 恢复方式 | 原因 |
|---|---|---|
| envelope 结构错误、缺/重 ID、空响应、batch Chat 重试后 provider error | 整个 batch → C1 单对 | 无法信任 item 边界 |
| envelope 完整，但某些 `true` 的 A/B 引文不合格 | batch 重试一次；仍失败时仅这些 pair → C1 单对 | 其余 ID 的完整 batch verdict 仍有可信边界 |

第二种选择性 fallback 防止“一个无证据正例拖累整组 8 个候选”，同时不直接接受该无证据
正例。`llm_single_fallback_count` 记录实际 fallback 单对调用数。

### 4.4 Fallback schema-drift 线索

exact claim-key 不匹配时，C2-B 会为该 fallback pair 从两侧 source chunk 当前 claims 中
选取至多两组 **fuzzy slot hints**：

```text
slot key = normalized claim_key（无 key 时 subject + predicate）
score    = character-bigram Jaccard
threshold = 0.35
max hints = 2
```

它们在 prompt 中明确标为“非 exact claim_key、非规则直判”。作用仅是帮助 batch LLM
定位可能的同一事实，例如：

```text
幽能引擎原型机 @ 测试时间 = 2150 年前
幽能引擎原型机测试 @ 计划开始时间 = 2153 年，status=已推迟
```

模型仍须从 A/B 原文引用中确认相同对象/事件和明确的新旧关系。该设计避免把 fuzzy
matching 当作规则判定，同时恢复 schema drift 下的 `version_update` 召回。

## 5. 成本与运行指标

迁移：

```text
migrations/versioned/000086_conflict_detection_runs.*
migrations/sqlite/000007_conflict_detection_runs.*
```

每一个 `conflict:detect` task 追加一行 `conflict_detection_runs`，包含完成、skip 与失败
三种状态。指标包括：

```text
candidate_claim_pairs
candidate_fallback_pairs
candidate_after_dedupe
candidates_submitted

rule_no_conflict
rule_direct_conflict
rule_needs_llm

llm_pair_count
llm_batch_call_count
llm_single_call_count
llm_single_fallback_count
llm_prompt_tokens
llm_completion_tokens

final_conflict_count
duration_ms
status
error_message
```

这些是冲突检测阶段的观测，不包括文档解析、embedding、claim extraction 或数据库查询
成本。`llm_pair_count` 是逻辑灰区 pair 数；batch/single counters 才是实际 provider
请求口径（含 retry / fallback）。

## 6. 可复现实验工具

核心工具：

```text
scripts/experiments/run_claims_eval.py
scripts/experiments/compare_conflict_runs.py
scripts/experiments/scenarios/c1_full.json
scripts/experiments/scenarios/p3_fallback.json
```

`c1_full` 同时包含：

- 3 个预期冲突文档对：P1、P2、P3/P4/P5；
- 12 个 `forbidden_conflict_document_pairs` 闭集负例断言；
- task 全部完成后重新查询 conflict，防止早到正例让后到误报未被导出。

常用命令：

```bash
make experiment-check
make experiment-v1
make experiment-c1
make experiment-c2-rules
make experiment-c2-batch
make experiment-c2-compare RUNS="<v1> <c1> <rules> <batch>"
```

`compare_conflict_runs.py` 将 detector integrity（预期对、禁止对、死信、task failure）与
legacy claim extractor 的自动 P/R gate 分开报告。它读取 artifact，不访问 API、Docker、
数据库或模型。

## 8. 已知限制与后续接口

1. C2-B 是 prompt + evidence-grounding 的研究原型，不是训练过的 NLI 模型；仍需多 seed
   和 holdout 语料测试；
2. fuzzy hint 是字符级 lexical signal，不是实体消歧或语义蕴含判断；仅可作为 LLM 注意力
   提示，不能提升为直接规则；
3. 当前 `version_update` 类型仍由 LLM 判断。文档生效日期、版本号、来源权威性和建议裁决
   属于 C3；
4. `knowledge_conflicts` 仍是 chunk-pair 粒度，raw 行数不能当作独立争议事实数；C4 将
   按 claim/fact 聚类为 `DisputedFact`；
5. C2 的成本表没有包含 claim extraction，不能描述为整个摄取 pipeline 的总成本下降；
6. `claims_eval` 是已参与开发的 calibration corpus；C2 运行中的 extractor P/R 波动不能
   单独用来证明或否定 C2 裁决层。
