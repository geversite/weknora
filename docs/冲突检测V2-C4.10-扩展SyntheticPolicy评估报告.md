## 1. 问题与范围

本评估不使用用户的私有/低质量业务文档，而是通过确定性生成的虚构 DOCX corpus，检查如下受控 policy 是否能在真实文件入口和真实服务链路中稳定执行：

```text
同 issuer 三来源唯一 winner
上传顺序与版本顺序脱钩
仅 date / 仅 version 的唯一最大来源
cross issuer
mixed issuer triplet
metadata missing
date/version direction disagreement
metadata tie
date interval overlap
```

真实执行链路：

```text
multipart file upload → DocReader → Asynq → claim extraction → C2 cascade
→ knowledge_conflicts → DisputedFact → C4.6 proposal
→ C4.7 explicit adoption → C4.8 durable reopen
```

每个 case 在新的 temporary KB 中运行；winner adoption 的 chunk disable/re-enable 不接触用户真实 KB 或文档。

计分定义：

```text
positive：只有预期 winner 为 TP；错误 winner 同时计 FP + FN；abstain 计 FN。

```

本报告以事实家族主口径为准，避免将同一 family 的三次 independent executions 当成三份独立事实样本。

## 5. Baseline 解释

这些 baseline 是刻意简化的反例参照，不是声称它们应当在现实系统中承担 authority policy。

### Latest upload

`latest_upload` 无条件选最后上传来源。它在乱序正例中漏选真正 winner，且在所有 no-proposal case 都会产生错误 proposal：

```text
fact-family policy accuracy: 0.167
unsafe actions: 6 / 6 negatives
```

### Date-only / version-only

这两个单信号 baseline 忽略 issuer 或另一种 recency signal。在 cross issuer、mixed issuer、metadata missing、direction disagreement 等模式中会产生不安全 proposal：

```text
fact-family policy accuracy: 0.667
unsafe actions: 3
```

### Raw C3 local vote

local vote 保留 pair-level metadata direction，因此在本 corpus 中维持 full positive recall；但无法要求 cluster 全部来源一致。它在 mixed issuer / metadata missing 拓扑中仍产生 proposal：

```text
fact-family policy accuracy: 0.833
unsafe actions: 2
```

### C4.6 global proposal

C4.6 只有在所有 cluster sources 具备一致 issuer、可比较且方向一致的 metadata，并存在唯一严格最大来源时才 proposal。本次 synthetic holdout 中：

```text
policy accuracy: 1.000
unsafe actions: 0
```

该结果证明的是上述显式 policy 在构造的反例覆盖中被正确执行；不证明真实 authority 或版本语义的普遍正确性。

## 6. Cluster 与 cascade 形状

Holdout 三次执行合计：

```text
raw conflicts: 84
DisputedFacts: 36
raw conflicts / DisputedFact: 2.333333
```

每次 execution 都满足：

```text
raw conflicts: 1–3
DisputedFacts: 1
```

说明每个设计的 fact family 维持了预期的一事实聚类形状。

C2 cascade 在本 holdout 的结果为：

```text
candidate claim pairs: 84
candidate fallback pairs: 0
rule direct conflicts: 84
rule needs LLM: 0
LLM batch/single calls: 0 / 0
prompt/completion tokens: 0 / 0
duration: 16,557 ms total; 459.917 ms per execution
```

这只能说明生成的简单、同句式数值 policy 在当前规则路径中可被直接处理。它不能替代已有 C1/C2 V1/C1/C2-B4 消融中的真实模型成本结论，也不能推断复杂文档的 LLM 成本。

Development R=1 中有 23 条 direct conflict 和 5 条 LLM conflict，说明模型/异步输入仍可能使简单 fixture 在 development run 中经过不同 cascade 分支；这也是 holdout 结果必须保留全部 artifact 而不能只报告最终 P/R 的原因。

## 7. 可以与不可以主张的结论

本报告支持：

```text
1. 在真实 HTTP、DocReader、Asynq、PostgreSQL 与配置模型链路中，C4.6 global proposal、C4.7 explicit adoption、
   C4.8 durable reopen 对 12 个未参与 development 调试的 controlled synthetic fact families 完成了 36/36 executions。
2. C4.6 在本构造 policy corpus 中避免了 latest-upload、date-only、version-only 与 raw C3 local-vote 的不安全 proposal。
3. 所有有效 holdout detector artifact 的 dead-letter count 都为 0，且三次 independent executions 的 prediction 一致。
4. 事实级聚类把 84 条 raw conflicts 投影为 36 个单事实 review/action units。
```

本报告不支持：

```text
1. 真实业务、法规或客户文档的 detection / winner accuracy；
2. PDF↔DOCX 跨格式事实聚类准确率（PDF 当前只完成单文件 ingress/claim smoke）；
3. 人工审阅准确率、Cohen's kappa 或用户工时节省；
4. provider RNG seed-controlled 因果结论；
5. 未显式建模的 authority hierarchy、范围差异或现实版本治理语义。
```
