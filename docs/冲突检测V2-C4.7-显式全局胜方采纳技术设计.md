## 1. 目标与边界

C4.6 只在 `DisputedFact` 上输出无副作用的唯一全局 winner proposal。C4.7 提供唯一的显式
采纳入口：

```text
人工/API 读取当前 DisputedFact
→ 审阅 winner / metadata evidence / source count
→ 回显完整 optimistic snapshot
→ 服务在 transaction 内重新验证
→ 全局 winner propagation
```

目标是解决 C4.5 不能安全处理 `newer_wins` / `older_wins` 的原因：一个 raw chunk-pair member
可能没有全局 winner，例如 V2 ↔ V1；若按局部 A/B 状态裁决，会把 V2 误记为该 row 的最终胜方。

C4.7 不接受调用方提交任意 winner 或任意 resolution。它只接受当前 C4.6 已提出的 winner，且
将所有 member 标记为方向无关的：

```text
resolved_global_winner
```

非目标：

- 不自动采纳模型 proposal；
- 不从 raw `resolved_newer_wins` / `resolved_older_wins` 推导 cluster action；
- 不采纳 `fuzzy_slot`、`document_singleton`、`chunk_pair` anchor；本期只允许 exact `claim_key`；
- 不实现 winner 撤销、再采纳、authority hierarchy 或多个 winner；
- 不添加前端 UI、i18n、wiki dispute block 或 agent narrative 改写；
- 不禁用 loser 文档的全部 chunks，只禁用该事实 cluster member 中属于 non-winner source 的具体 chunks。

## 2. API

```text
POST /api/v1/knowledge-bases/:id/conflicts/clusters/adopt-winner
```

权限与既有 Resolve 一致：`OwnedKBOrAdmin + KBAccessWrite`，API key 需要 ingest/full capability。

请求必须带上从当前 `GET /conflicts/clusters` 读取的全部 optimistic snapshot：

```json
{
  "disputed_fact_id": "<cluster id>",
  "expected_winner_knowledge_id": "<suggested_winner_knowledge_id>",
  "expected_proposal_version": "c3-c4-v1",
  "expected_proposal_updated_at": "2026-09-02T00:00:00Z",
  "expected_proposal_source_count": 3,
  "note": "optional human audit note"
}
```

`expected_proposal_updated_at` 是 DisputedFact 当前 `updated_at`。它不是客户端生成的时间；调用方
必须原样回显 GET 响应。任一 expected 字段缺失或格式非法为 HTTP `400`；proposal/state 已变化、
缺 proposal、cluster 已部分裁决等当前状态冲突为 HTTP `409`。

成功返回：

```json
{
  "disputed_fact_id": "...",
  "resolution": "resolved_global_winner",
  "winner_knowledge_id": "...",
  "proposal_version": "c3-c4-v1",
  "proposal_confidence": 0.99,
  "proposal_source_count": 3,
  "adoption_version": "c4-winner-adopt-v1",
  "updated_conflict_ids": ["..."],
  "disabled_chunk_ids": ["..."],
  "disabled_knowledge_ids": ["..."],
  "clear_penalty_chunk_ids": ["..."],
  "rebuild": {"pending_conflict_count": 0}
}
```

## 3. Fail-closed transaction

`KnowledgeConflictRepository.AdoptPendingWinnerProposal` 在单一 database transaction 中按以下顺序执行：

```text
lock DisputedFact
→ 检查 exact claim_key / pending / current winner / proposal version /
  source count / updated_at 与请求快照完全一致
→ lock 当前 cluster 的全部 raw members
→ 检查 member count == fact conflict_count == pending_conflict_count，且每行均 pending
→ 从所有 member 收集 source 和 loser chunk owner
→ 检查 source count 与 proposal source count 一致，winner 位于当前 source set
→ lock 全部 member chunks，并核验每个 raw A/B side 的 knowledge ownership 与 enabled state
→ transaction 内禁用 non-winner target chunks
→ transaction 内把全部 member 更新为 resolved_global_winner、resolved_by、resolved_at、审计 note
→ transaction 内将 DisputedFact 更新为 resolved / pending_conflict_count=0
→ 退出 transaction 后执行 canonical cluster rebuild
```

任一步失败会 rollback 前面的 chunk/status 更新。特别地，以下情况不能产生部分副作用：

```text
过期 updated_at、winner/version/source count 变化
新 raw member 尚未由 C4 rebuild 纳入 aggregate
已有局部 Resolve 导致部分 member 非 pending
proposal 消失、跨 issuer 导致空 proposal
winner 不在 member source set
raw conflict 的 knowledge/chunk 为空、任一 member chunk 已禁用，或 chunk ownership 不一致
```

rebuild 在已经成功的 transaction 后是 canonical aggregate 收敛步骤；若其失败，原子 adoption
本身不会回滚，服务返回明确错误，管理员可调用已有 `/clusters/rebuild` 收敛 aggregate。

## 4. 全局传播语义

对每个 pending member 的 A/B side，服务根据 **source knowledge ID 是否等于已采纳 winner** 分类，而
不是根据 A 是新上传、B 是旧上传，或其局部 C3 `suggested_resolution` 分类：

| member side | 动作 |
|---|---|
| `knowledge_id == winner_knowledge_id` | 保持该 member chunk enabled |
| `knowledge_id != winner_knowledge_id` | 禁用该 member chunk |
| 所有 member rows | `status=resolved_global_winner`、`auto_resolved=false` |

因此一个 V2 ↔ V1 member 即使不直接包含 V3，也会被标记为 `resolved_global_winner`，且 V2、V1 的
cluster member chunks 均作为 global loser targets 被禁用。V3 member chunks 保持 enabled。

`resolution_note` 以不可伪造的服务端前缀记录：

```text
[c4.7:c4-winner-adopt-v1]
explicitly adopted global winner=<knowledge id>
proposal_version=<version>
source_count=<count>
```

随后才附加人工 `note`。`auto_resolved` 始终写为 `false`，因为这是显式用户/API 行为而不是模型自动动作。

## 5. 测试与可重复实验

Go 覆盖：

```text
TestAdoptPendingWinnerProposalUsesGlobalWinnerAndDisablesOnlyLosers
  - V2 ↔ V1（不含 V3）仍用 global status 解析
  - V1/V2 chunks disabled，V3 chunk enabled
  - raw rows / DisputedFact / audit note 一致

TestAdoptPendingWinnerProposalRejectsStaleSnapshotWithoutMutation
  - 过期 updated_at snapshot 返回 current-state conflict
  - raw rows、chunks、DisputedFact 均不变

TestAdoptPendingWinnerProposalRejectsDisabledMemberChunkWithoutMutation
  - 任一已禁用 member chunk 保持拒绝，避免把部分状态伪装成新采纳

TestAdoptPendingWinnerProposalRejectsNonExactFactAnchor
  - fuzzy_slot cluster 保持不可采纳

TestAdoptDisputedFactWinnerPropagatesOnlyExplicitGlobalWinner
  - service 入口完成 rebuild 后 aggregate 收敛
```

真实服务实验只使用脚本和 public HTTP API：

```bash
# 创建 fresh pending C4.6 正例，再验证 stale rejection + explicit adoption
make experiment-c46
POS_RUN="$(ls -td experiments/runs/*-c46_global_winner_triplet-c2-rules-* | head -1)"
make experiment-c47 RUN="$POS_RUN"

# 创建 fresh 跨 issuer 无 proposal 负例，再验证 HTTP 409 / no mutation
make experiment-c46-negative
NEG_RUN="$(ls -td experiments/runs/*-c46_cross_issuer_no_proposal-c2-rules-* | head -1)"
make experiment-c47-negative RUN="$NEG_RUN"
```

`scripts/experiments/run_winner_adoption.py` 使用 PostgreSQL **只读**导出验证，并写入：

```text
<positive-run>/winner_adoption.json
<negative-run>/winner_adoption_negative.json
```

正例在成功请求前会故意提交一个 stale `expected_proposal_version`，要求 HTTP `409` 且所有 rows/chunks
不变；之后才用 live GET 读取的精确 snapshot 采纳。负例故意尝试采纳空 proposal，要求 HTTP `409` 且
无 mutation。
