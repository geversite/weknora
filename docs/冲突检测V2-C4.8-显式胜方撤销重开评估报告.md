## 1. 结论

C4.8 已在真实服务中验证一个 C4.7 global winner adoption 的可审计、fail-closed reopen：

```text
fresh C4.6 proposal
→ C4.7 生成 durable adoption record 并禁用 loser chunks
→ C4.8 先拒绝 stale reopen（HTTP 409 / no mutation）
→ C4.8 精确 re-enable record 中的 target chunks
→ 同一 adoption 的 raw members 回到 pending
→ adoption record adopted → revoked
→ DisputedFact 回到 pending，C4.6 proposal 保留
```

正例与负例均通过：

| 场景 | C4.7 / C4.8 动作 | 结果 |
|---|---|---|
| 同 issuer V1/V2/V3 | adoption → stale reopen → exact reopen | 3 条 raw member `resolved_global_winner → pending`；2 个 recorded loser chunks `disabled → enabled`；record `adopted → revoked` |
| 跨 issuer、无 adoption | attempted reopen | HTTP 409；2 条 raw member、3 个 member chunks、DisputedFact 均无 mutation |

C4.8 不恢复“当前看起来像 loser 的所有 chunk”，而是只恢复 migration `000092` 后 durable record 中的
`disabled_chunk_ids`。它同时验证 cluster member set、source set、winner proposal、adoption ID、chunk owner、
chunk enabled state 与 adoption-time timestamp。任何一个条件变化都拒绝执行。

上游真实 C4.6 run：

```text

C2 LLM(batch/single): 0 / 0
C3 local suggestions: 3 × resolved_newer_wins
```

### 2.1 C4.7 durable adoption

C4.7 从 live cluster snapshot 读取并回显：

```text
winner_knowledge_id:       0ed01596-d51d-4627-84fd-ddb23ea54ef5 (c46_v3)
proposal_version:          c3-c4-v1
proposal_confidence:       0.99
proposal_source_count:     3
expected_proposal_updated_at: 2026-09-02T13:13:47.334681+08:00
```

其 stale proposal-version probe 正确返回 HTTP `409`，并验证 raw members / chunks 不变。精确 request
随后生成 durable record：

```text
winner_adoption_id: 93e32a83-d454-4fb8-a5a4-08139dd41ce6
status: adopted
member_conflict_ids: 3
disabled_chunk_ids: 2
disabled_knowledge_ids: 2
adopted_at: 2026-09-02 05:13:49.674737+00
```

此时：

```text
raw members: 3 × resolved_global_winner
raw winner_adoption_id: 全部等于 93e32a83-d454-4fb8-a5a4-08139dd41ce6
DisputedFact.status: resolved
DisputedFact.pending_conflict_count: 0
DisputedFact.active_winner_adoption_id: 93e32a83-d454-4fb8-a5a4-08139dd41ce6
winner chunks: enabled
recorded loser chunks: disabled
```

### 2.2 stale reopen 必须没有副作用

C4.8 先故意提交过期 `expected_disputed_fact_updated_at`，服务返回：

```text
HTTP 409
error code: 1005 (conflict)
reason: disputed fact snapshot is stale; refresh before reopening
members_unchanged: true
chunks_unchanged: true
adoption_unchanged: true
```

因此 stale reviewer snapshot 不会提前 re-enable chunks，也不会将 adoption record 标成 revoked。

### 2.3 精确 reopen

随后将当前 active adoption ID 与 live `updated_at` 原样回显，返回：

```text
winner_adoption_id: 93e32a83-d454-4fb8-a5a4-08139dd41ce6
winner_knowledge_id: 0ed01596-d51d-4627-84fd-ddb23ea54ef5 (c46_v3)
reopen_version: c4-winner-reopen-v1
reopened_conflict_count: 3
reenabled_chunk_ids: 2
```

只读 PostgreSQL artifact 验证：

```text
3 / 3 raw members:
  status = pending
  winner_adoption_id = ""
  auto_resolved = false
  resolved_by = ""
  resolved_at = NULL
  resolution_note = [c4.8:c4-winner-reopen-v1] ... winner_adoption_id=93e...

3 / 3 member chunks:
  is_enabled = true

DisputedFact:
  status = pending
  pending_conflict_count = 3
  active_winner_adoption_id = ""
  suggested_winner_knowledge_id = 0ed01596-d51d-4627-84fd-ddb23ea54ef5
  winner_proposal_version = c3-c4-v1
  winner_proposal_source_count = 3

Durable adoption record:
  status = revoked
  original winner / proposal version preserved
  revoked_at = 2026-09-02 05:13:52.015048+00
  revoke_note = [c4.8:c4-winner-reopen-v1] ...
```

这个结果证明 reenable 集不是“所有 raw member chunks”或“整份 loser document”：C4.7 record 中只有两个
`disabled_chunk_ids`，C4.8 也只重启这两个；winner chunk 从 adoption 前到 reopen 后始终 enabled。

```text
KB:         359ecb98-917d-4352-83bb-33adb10d7a99
```

上游跨 issuer 场景的真实结果：

```text

disputed facts: 1
raw / cluster: 2.000
C2 rules(no/direct/LLM): 0 / 1 / 1
C2 LLM(batch/single): 0 / 1

```

C4.6 因 issuer 不一致没有 winner proposal，因此没有 C4.7 active adoption。C4.8 尝试 reopen 时返回：

```text

reason: disputed fact has no active winner adoption to reopen
```

调用前后均为：

```text

DisputedFact.pending_conflict_count=2

suggested_winner_knowledge_id=""
winner_proposal_version=""
```

这证明 C4.8 不能被用作任意 chunk enable API，也不能绕过 C4.6/C4.7 强行恢复或指定权威来源。

## 4. 数据模型、接口与迁移边界

Migration `000092` / SQLite `000013` 新增：

```text
knowledge_conflicts.winner_adoption_id
disputed_facts.active_winner_adoption_id
disputed_fact_winner_adoptions
```

后一张表存储 C4.7 adoption 的 immutable-in-practice evidence：winner、proposal snapshot、member IDs、
disabled chunk/knowledge IDs、adoption actor/time/note。C4.8 仅追加 revoke fields 并将 record 状态改为
`revoked`，不会覆盖原始 evidence。

API：

```text
POST /api/v1/knowledge-bases/:id/conflicts/clusters/reopen-winner
```

它要求：

```text
disputed_fact_id
winner_adoption_id
expected_disputed_fact_updated_at
optional note
```

C4.8 与 C4.7 都不是自动任务；只有带现有 KB write 权限的 owner/admin 或对应 API key 显式请求才能执行。
迁移前 C4.7 action 没有 durable record，C4.8 会安全拒绝，而不是从 note 或当前 cluster 反推 target。

## 5. 关闭条件与限制

**C4.8 关闭条件：通过（explicit reopen 研究原型）。**

- [x] PostgreSQL `000092` / SQLite `000013` durable adoption schema；
- [x] C4.7 新 action 持久化 record、raw member ID 与 aggregate active ID；
- [x] C4.8 stale updated-at guard：HTTP 409，raw/chunks/record 无 mutation；
- [x] C4.8 exact reopen：3 raw members pending、2 recorded loser chunks enabled、record revoked；
- [x] winner chunk 保持 enabled，C4.6 proposal / source count 保留；
- [x] no-active-adoption 跨 issuer负例：HTTP 409、2 raw members / 3 chunks / fact 无 mutation；
- [x] 上游 C4.6 正、负 run 的 dead letters 均为 0；
- [x] public HTTP API + real PostgreSQL + Asynq 上游 detection + script artifact；
- [x] 无自动 reopen、无 UI、无 wiki dispute block、无 agent narrative 写回。

仍未完成、也不应宣称完成：

- 多 seed、真实法规/产品版本集和第二审阅者上的 proposal/adoption/reopen 准确率；
- `fuzzy_slot`、`document_singleton`、`chunk_pair` 的 adoption/reopen；
- concurrent multi-process race / distributed lock 压测、复杂外部 chunk mutation 和 crash-recovery；
- 跨 conflict 的 reference-aware chunk disable/reenable policy；
- wiki dispute block、agent narrative 整合、审批 UI、灰度与配额。

reopen 后若要再次采纳 winner，必须重新走 C4.7 的 explicit snapshot 审核；C4.8 不会自动再采纳，也不会
选择替代 winner。
