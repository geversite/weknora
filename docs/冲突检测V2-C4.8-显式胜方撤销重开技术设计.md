> [C4.7 显式全局胜方采纳评估报告](冲突检测V2-C4.7-显式全局胜方采纳评估报告.md)。

## 1. 目标与边界

C4.7 可以由 owner/admin 明确采纳一个 C4.6 global winner，并禁用对应 loser member chunks。如果新
证据表明这一决定需要重新审查，C4.8 提供**显式、可审计、fail-closed**的 reversal：

```text
当前 active C4.7 adoption
→ 人工/API 明确请求 reopen
→ 回显 adoption ID + 当前 DisputedFact updated_at
→ transaction 内确认原始 adoption、raw members、disabled chunks 仍完全匹配
→ 仅 re-enable 该 adoption 当初禁用的 chunks
→ raw members 恢复 pending
→ DisputedFact 恢复 pending review
```

C4.8 不是“把任意 disabled chunk 重新打开”的通用接口，也不允许调用方提交新的 winner。它只回滚一个
当前 active、带完整 durable record 的 C4.7 adoption。reopen 后若仍要采用 winner，必须重新经过 C4.7 的
显式 snapshot 校验；C4.8 不会自动再采纳或选择替代 winner。

非目标：

- 不自动 reopen，也不因新上传文档自动撤销 winner；
- 不回滚 C4.5 `keep_both` / `not_conflict` 或 legacy raw-pair Resolve；
- 不支持 C4.8 migration `000092` 之前已经执行的 legacy C4.7 adoption；
- 不对 `fuzzy_slot`、`document_singleton`、`chunk_pair` 做 adoption/reopen；
- 不重新评估 C4.6 metadata、issuer hierarchy、版本权威性或模型输出；
- 不写 wiki dispute block、不触发 agent 叙事改写、不做 UI/i18n。

## 2. Durable adoption identity

仅凭 raw `status=resolved_global_winner` 和 `resolution_note` 无法安全判断哪些 chunks 是某次 adoption
专门禁用的。因此 migration `000092` 引入三层持久化身份：

```text
knowledge_conflicts.winner_adoption_id
  → 每条 active resolved_global_winner member 指向同一个 adoption record

disputed_facts.active_winner_adoption_id
  → 只有全部 members 均由同一个 active adoption 拥有时才非空

disputed_fact_winner_adoptions
  → adoption 的 winner、proposal snapshot、member IDs、disabled chunk IDs、
    disabled knowledge IDs、actor/time/note，以及后续 revoked audit fields
```

`disputed_fact_winner_adoptions` 对 `(tenant_id, knowledge_base_id, disputed_fact_id)` 建立
`status='adopted'` 的 partial unique index，因此一个 fact 同时只能有一个 active adoption。被撤销的记录
保留 `status=revoked`、`revoked_by`、`revoked_at`、`revoke_note`；原始 winner/member/chunk evidence 不被覆盖。

C4 rebuild 只在以下条件同时满足时派生 `active_winner_adoption_id`：

```text
conflict_count > 0
pending_conflict_count == 0
全部 member status == resolved_global_winner
全部 member 的 winner_adoption_id 非空且完全相同
```

这让 legacy C4.7 action（migration 前没有 durable record）、混合裁决、局部 Resolve 或新 pending
member 都保持空 active ID，C4.8 会拒绝而非猜测。

## 3. API

```text
POST /api/v1/knowledge-bases/:id/conflicts/clusters/reopen-winner
```

权限与 C4.7 adoption 一致：`OwnedKBOrAdmin + KBAccessWrite`；API key 需要 ingest/full capability。

调用方先从 `GET /conflicts/clusters?status=resolved` 读取当前 aggregate，然后原样回显：

```json
{
  "disputed_fact_id": "<cluster id>",
  "winner_adoption_id": "<current active_winner_adoption_id>",
  "expected_disputed_fact_updated_at": "2026-09-02T00:00:00Z",
  "note": "optional human reopen reason"
}
```

字段缺失或时间格式非法为 HTTP `400`。当前 state 不再可回滚时返回 HTTP `409`：active ID 不同/为空、
updated_at 过期、record 缺失或已 revoked、member set 改变、shared chunk ownership、chunk 已被外部修改等。

成功返回：

```json
{
  "disputed_fact_id": "...",
  "winner_adoption_id": "...",
  "winner_knowledge_id": "...",
  "reopen_version": "c4-winner-reopen-v1",
  "reopened_conflict_ids": ["..."],
  "reenabled_chunk_ids": ["..."],
  "rebuild": {"pending_conflict_count": 3}
}
```

## 4. Fail-closed reopen transaction

`KnowledgeConflictRepository.ReopenWinnerAdoption` 使用一个 database transaction：

```text
lock DisputedFact
→ 检查 status=resolved、active_winner_adoption_id 与 request 一致、updated_at 一致
→ lock durable adoption record，检查 status=adopted 且 proposal/winner 仍匹配 fact
→ lock 全部 current cluster members
→ 检查 member IDs == durable member_conflict_ids，且每条均为
  resolved_global_winner + 相同 winner_adoption_id
→ 由 raw member 重新推导 loser chunk set，并与 durable disabled_chunk_ids 比对
→ lock durable target chunks，验证仍 disabled、knowledge owner 不变、updated_at 仍等于 adopted_at
→ 在 chunk lock 下拒绝任何同一 target 被另一 active/legacy global adoption 占用
→ transaction 内 re-enable target chunks
→ transaction 内把全部 member 改回 pending，清空 winner_adoption_id / resolved_by / resolved_at
→ transaction 内清空 fact.active_winner_adoption_id，并将 fact 设为 pending
→ transaction 内将 adoption record 标记 revoked，写入 revoke audit fields
→ 后续 canonical cluster rebuild
```

每个检查都在写入前完成；任一失败回滚 transaction。因此 C4.8 不会把已被另一次决策、手工更新或新
证据改变过的 disabled chunk 误重新启用。

reopen 后 raw row 的 `resolution_note` 写入服务端 C4.8 prefix，表明它已被重新打开；原 C4.7
adoption 的完整历史留在 `disputed_fact_winner_adoptions`，而不是依赖即将恢复 pending 的 raw row。

若 transaction 已成功但后续 canonical rebuild 失败，原子 reopen 不回滚；服务明确返回错误，管理员可以调用
已有 `/conflicts/clusters/rebuild` 收敛 aggregate。这与 C4.5/C4.7 的既有 "side effect 成功后 best-effort
rebuild" 边界一致。

## 5. 生命周期与迁移编号

- KB 删除时，`DisputedFactRepository.DeleteByKB` 会同时删除该 KB 的 adoption audit rows；
- 单份 knowledge 删除后若 raw cluster 不再完整，rebuild 会清空 active adoption ID，C4.8 只能拒绝 reopen；
  audit row 保留为历史证据；
- migration 前已经执行的 C4.7 adoption 没有 durable record，明确不可通过 C4.8 reopen；
- C4.8 占用 PostgreSQL `000092` / SQLite `000013`，原规划中的 C7 patch proposal migration 顺延为
  PostgreSQL `000093` / SQLite `000014`。

## 6. 测试与可重复实验

Go 测试：

```text
TestReopenWinnerAdoptionRestoresOnlyRecordedState
  - C4.7 record / raw members / chunks → pending / enabled / revoked record

TestReopenWinnerAdoptionRejectsStaleSnapshotWithoutMutation
  - 过期 DisputedFact updated_at → current-state conflict，状态不变

TestReopenWinnerAdoptionRejectsChunkOwnedByAnotherActiveAdoption
  - shared target chunk → fail closed，不重新启用

TestStringArrayValueScan
  - SQLite TEXT string 与 PostgreSQL []byte JSON arrays 均可读取 audit record
```

真实服务实验：

```bash
# Fresh C4.6 proposal → fresh C4.7 durable adoption → C4.8 reopen
make experiment-c46
POS_RUN="$(ls -td experiments/runs/*-c46_global_winner_triplet-c2-rules-* | head -1)"
make experiment-c47 RUN="$POS_RUN"
make experiment-c48 RUN="$POS_RUN"

# Fresh C4.6 cross-issuer/no-adoption cluster → C4.8 must reject
make experiment-c46-negative
NEG_RUN="$(ls -td experiments/runs/*-c46_cross_issuer_no_proposal-c2-rules-* | head -1)"
make experiment-c48-negative RUN="$NEG_RUN"
```

`run_winner_reopen.py` 先故意发送 stale updated_at，要求 HTTP `409` 且 member/chunk/adoption record 不变；
再通过 live API 的精确 snapshot 执行 reopen。产物：

```text
<positive-run>/winner_reopen.json
<negative-run>/winner_reopen_negative.json
```

## 7. 关闭条件

C4.8 在以下证据完成前不能冻结：

- [ ] PostgreSQL `000092` / SQLite `000013` migration 与 C4.8 environment preflight；
- [ ] Go repository/service tests 与 `go build ./...`；
- [ ] 正例 stale reopen：HTTP 409，raw/chunks/adoption record 无 mutation；
- [ ] 正例 exact reopen：raw members 重新 pending、record revoked、only recorded loser chunks reenabled；
- [ ] winner chunk 仍 enabled，C4.6 proposal 保留、DisputedFact pending；
- [ ] 无 active adoption 负例：HTTP 409/no mutation；
- [ ] 真实 HTTP API、PostgreSQL、Asynq 上游 detection、脚本 artifact 与评估报告；
- [ ] 无自动 reopen、无 UI、无 wiki/agent 写回。
