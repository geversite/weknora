## 1. 结论

C4.7 已在真实服务中验证从 **C4.6 advisory proposal** 到 **人工/API 显式采纳** 的最小安全闭环：

```text
GET current DisputedFact proposal
→ 调用方回显 winner / proposal version / source count / updated_at snapshot
→ 服务 transaction 内锁定并重读 aggregate、raw members、member chunks
→ stale / no-proposal / partial state 一律 HTTP 409、无 mutation
→ 明确采纳后以 global winner（不是 raw A/B 方向）传播
```

正例和负例均通过：

| 场景 | 当前 proposal | API 结果 | raw members | chunks | DisputedFact |
|---|---|---|---|---|---|
| 同 issuer V1/V2/V3 | V3，confidence 0.99，3 sources | stale request 409/no mutation；精确 request 成功 | 4/4 → `resolved_global_winner` | winner member chunk 保持 enabled；3 个 loser member chunks disabled | `resolved`，pending=0 |
| 跨 issuer V1/V3 | 空 | 409/no mutation | 1 条仍 `pending` | 2 个 member chunks 仍 enabled | 仍 `pending`，pending=1 |

C4.7 没有自动调用：只有 `POST /conflicts/clusters/adopt-winner` 才会执行 mutation。它也没有把
C4.5 的通用 `resolved_newer_wins` / `resolved_older_wins` 打开；全部 member 统一使用方向无关的
`resolved_global_winner`，从而避免 V2 ↔ V1 这类不包含全局 V3 winner 的 raw pair 被局部 A/B
方向错误解释。

## 2. 真实正例：同 issuer 三来源显式采纳

```text
C4.6 source run: 20260902T041854Z-c46_global_winner_triplet-c2-rules-caed28fe
KB:            2800a66b-f62b-4c6f-bf91-302872e8e6b1
DisputedFact:  70a28789-a473-430b-8eca-5c7700a71293
```

上游 C4.6 已在这个临时 KB 中生成一个 `claim_key` cluster：

```text
claims: 4
raw conflicts: 4
disputed facts: 1
raw / cluster: 4.000
C2 rules(no/direct/LLM): 0 / 3 / 1
C2 LLM(batch/single): 0 / 1
C3 local suggestions: 4 × resolved_newer_wins
C4.6 winner proposals: 1
```

被审阅并原样回显的 C4.6 snapshot：

```text
winner_knowledge_id:       5efd1863-9ad4-4f73-a0ca-2b45b017e2c4 (c46_v3)
proposal_version:          c3-c4-v1
proposal_confidence:       0.99
proposal_source_count:     3
expected_proposal_updated_at: 2026-09-02T12:22:40.924134+08:00
```

### 2.1 先拒绝 stale snapshot

action verifier 首先故意把 `expected_proposal_version` 改为错误值。服务返回：

```text
HTTP 409
error code: 1005 (conflict)
reason: proposal version changed; refresh the disputed fact before adoption
members_unchanged: true
chunks_unchanged: true
```

这证明 optimistic guard 在写入前生效；过期 reviewer snapshot 不会将 winner/loser 状态部分落库。

### 2.2 精确 snapshot 显式采纳

随后使用 live `GET /conflicts/clusters` 的完整 snapshot 请求成功：

```text
resolution:              resolved_global_winner
winner_knowledge_id:     5efd1863-9ad4-4f73-a0ca-2b45b017e2c4 (c46_v3)
proposal_version:        c3-c4-v1
proposal_confidence:     0.99
proposal_source_count:   3
adoption_version:        c4-winner-adopt-v1
updated_conflict_count:  4
disabled_chunk_ids:      3
disabled_knowledge_ids:  2
clear_penalty_chunk_ids: 4
```

所有四条 member row 均验证为：

```text
status = resolved_global_winner
auto_resolved = false
resolution_note = [c4.7:c4-winner-adopt-v1] explicitly adopted global winner=...
                  proposal_version=c3-c4-v1 source_count=3 ...
```

其中前两条 raw rows 的双方都是 V2/V1，并**不包含 V3**；它们仍统一使用
`resolved_global_winner`，而不是误标为“V2 newer wins”。其余两条 row 是 V3↔V1、V3↔V2。
这提供了“global source identity 优先于 raw A/B orientation”的真实证据。

chunk 状态的只读 PostgreSQL 导出为：

```text
winner source member chunk: 1 / 1 enabled
V1 source member chunks:   2 / 2 disabled
V2 source member chunks:   1 / 1 disabled
```

aggregate 最终保持 C4.6 proposal，并收敛为：

```text
status = resolved
pending_conflict_count = 0
suggested_winner_knowledge_id = 5efd1863-9ad4-4f73-a0ca-2b45b017e2c4
winner_proposal_version = c3-c4-v1
winner_proposal_source_count = 3
```

## 3. 真实负例：跨 issuer / 空 proposal

```text
C4.6 source run: 20260902T042243Z-c46_cross_issuer_no_proposal-c2-rules-caed28fe
KB:            15464921-deac-4216-a498-13b31c8a77fd
DisputedFact:  ace9931c-6c15-4857-8d3f-9d27a6fc26c2
```

这个 KB 有一条 exact `claim_key` raw conflict 和一个 pending cluster，但 C4.6 因 issuer 不同而
保持所有 winner proposal 字段为空。C4.7 verifier 故意调用 `adopt-winner`，服务返回：

```text
HTTP 409
error code: 1005 (conflict)
reason: disputed fact ... has no adoptable global winner proposal
```

调用前后只读导出一致：

```text
raw member status: pending
auto_resolved: false
member chunks: 2 / 2 enabled
DisputedFact.status: pending
DisputedFact.pending_conflict_count: 1
suggested_winner_knowledge_id: ""
winner_proposal_version: ""
```

因此 C4.7 不能被用于“手工强行指定一个更晚文档”为胜方；缺失 C4.6 proposal 是硬拒绝条件，而不是
允许 caller 覆盖的提示。

## 4. 实现边界与可重复性

API：

```text
POST /api/v1/knowledge-bases/:id/conflicts/clusters/adopt-winner
```

请求必须包含：

```text
disputed_fact_id
expected_winner_knowledge_id
expected_proposal_version
expected_proposal_updated_at
expected_proposal_source_count
optional note
```

服务只允许：

```text
pending + exact claim_key + current non-empty C4.6 proposal
```

并在一个 database transaction 中锁定 aggregate、全部 current members 和全部 member chunks。以下情形
均 fail closed：proposal/winner/version/source count/timestamp 不匹配、member count 与 aggregate 不一致、
任何 member 非 pending、任何 member chunk 已禁用、winner 不在 source set 或 chunk ownership 不匹配。

可重复命令：

```bash
make experiment-c46
POS_RUN="$(ls -td experiments/runs/*-c46_global_winner_triplet-c2-rules-* | head -1)"
make experiment-c47 RUN="$POS_RUN"

make experiment-c46-negative
NEG_RUN="$(ls -td experiments/runs/*-c46_cross_issuer_no_proposal-c2-rules-* | head -1)"
make experiment-c47-negative RUN="$NEG_RUN"
```

验证脚本只通过 public HTTP API 触发 mutation；PostgreSQL 仅以只读方式核验，并输出：

```text
<positive-run>/winner_adoption.json
<negative-run>/winner_adoption_negative.json
```

## 5. C4.7 关闭条件与限制

**关闭条件：通过（explicit-only 研究原型）。**

- [x] owner/admin + API key write path 的 `adopt-winner` endpoint；
- [x] 当前 proposal 的 winner/version/source-count/updated-at optimistic guard；
- [x] stale proposal HTTP 409 且 raw members/chunks 不变；
- [x] 同 issuer V1/V2/V3 正例：4 个 raw members 一次传播为 `resolved_global_winner`；
- [x] global winner member chunk 保留 enabled，3 个 loser member chunks disabled；
- [x] DisputedFact 收敛为 `resolved` / `pending_conflict_count=0`，C4.6 proposal 保留；
- [x] 跨 issuer / 空 proposal 负例：HTTP 409，raw/chunks/fact 无 mutation；
- [x] `auto_resolved=false`、服务端 audit-note prefix 和 direction-free status 的真实导出；
- [x] 实验 runner 不直接写 PostgreSQL；
- [x] 无自动采纳、无 UI、无 wiki dispute block、无 agent narrative 写回。

仍未完成、也不应宣称完成：

- 多 seed、真实法规/产品版本语料、第二审阅者与 adoption precision/recall；
- `fuzzy_slot` / `document_singleton` / `chunk_pair` 的 adoption（当前明确拒绝）；
- winner proposal 的撤销、重开、再采纳、并列 winner、issuer hierarchy；
- 将被禁用 chunk 的后续 wiki/agent 叙事处理；
- 面向生产并发/高吞吐的分布式锁、审批 UI、配额和灰度。

C4.7 之后，不应自动继续扩展副作用。下一项研究工作应先选择一个可单独评估的问题，例如：

```text
winner adoption 的撤销 / reopen 协议
或
真实多来源版本集上的 proposal / adoption 人工准确率
```

而不是直接进入 wiki 写回或端到端治理。
