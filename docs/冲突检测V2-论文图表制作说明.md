## 1. 先生成可编辑 SVG

五张图均可由纯 Python 标准库脚本生成，不依赖 Graphviz、Matplotlib、浏览器或图像模型：

```bash
cd ~/weknora

FIGURE_OUT="$HOME/weknora-paper-assets/conflict-v2-figures"
mkdir -p "$FIGURE_OUT"

python3 scripts/paper_figures/generate_conflict_v2_figures.py \
  --output-dir "$FIGURE_OUT"
```

生成：

```text
fig1_system_architecture.svg
fig2_fact_lifecycle.svg
fig3_cascade_cost_ablation.svg
fig4_holdout_baselines.svg
fig5_fail_closed_state_machine.svg
figures_manifest.json
README.md
```

SVG 是矢量图，可用 Inkscape、Figma、Illustrator、draw.io 或浏览器打开。若本机安装 Inkscape，可转为 PDF：

```bash
cd "$FIGURE_OUT"
inkscape fig1_system_architecture.svg --export-type=pdf
```

脚本数据来源：

```text
图 3：C2-B4 final cost ablation
图 4：C4.10 extended synthetic holdout 的 fact-family 主口径
图 1/2/5：冻结的 C1→C4.8 架构和安全协议
```

不要把图 4 的 controlled-synthetic scope footer 裁掉；若按 venue 样式去掉 footer，必须在图注保留同等限定。

## 2. 图表清单与论文位置

| 图 | 文件 | 正文位置 | 图注核心 |
|---|---|---|---|
| 图 1 | `fig1_system_architecture.svg` | 第 3 节开头 | 从 claim extraction 到 explicit、可撤销 winner lifecycle 的系统架构 |
| 图 2 | `fig2_fact_lifecycle.svg` | 第 3.3–3.5 节 | 多条 raw conflicts 聚成一个 DisputedFact，局部方向不直接成为全局 action |
| 图 3 | `fig3_cascade_cost_ablation.svg` | 第 5.3 节 | C2-B4 相对 C1 的 LLM calls、Token 与时延成本消融 |
| 图 4 | `fig4_holdout_baselines.svg` | 第 5.6 节 | C4.6 与 latest/date/version/local-vote baseline 的 policy accuracy 与 unsafe actions |
| 图 5 | `fig5_fail_closed_state_machine.svg` | 第 3.5 节或第 6 节 | proposal、explicit adoption、durable reopen 与 HTTP 409 fail-closed 分支 |

### 建议图注

**图 1：** WeKnora Conflict Detection V2 的事实级冲突治理架构。系统将文档/Wiki 内容抽取为 claims，经精确和 fallback 候选、C2 cascade 裁决生成 raw conflicts，再聚合为 DisputedFacts。C4.6 的 proposal 无副作用；C4.7/C4.8 的 action 仅在显式 snapshot 与 durable record 条件下执行。

**图 2：** 三个版本来源的三条 raw conflicts 被聚合为一个 DisputedFact。只有当所有来源的 issuer/date/version evidence 一致且存在唯一严格最大来源时，系统才产生 advisory proposal；adoption 与 reopen 均为显式、可审计操作。

**图 3：** 在相同 C1 full scenario 上，C2-B4 将 LLM 调用从 48 降至 9，并降低 Token 与检测时延。该结果为固定受控场景的真实服务成本消融。

**图 4：** 在 12 个构造的 synthetic holdout fact families 上，C4.6 global proposal 与简化 baseline 的比较。每个 fact family 只有在全部三次 independent replicates 正确时才计为正确；该图不是真实业务文档准确率。

**图 5：** explicit adoption / durable reopen 的 fail-closed 状态机。任何 metadata、snapshot、member topology 或 target state 不匹配均返回 HTTP 409 且不产生 mutation。

## 3. 统一视觉规范

建议所有图保持：

```text
画布：白底，横向 16:9 或 A4 双栏宽度
字体：Noto Sans CJK SC / 思源黑体 / Microsoft YaHei
主文字：深蓝 #17324D
claim / architecture：蓝 #2878B5
metadata / proposal：青绿 #1E9E89
explicit action：橙 #ED8A19
fail-closed / unsafe：红 #D95D54
reopen / durable record：紫 #7664C5
```

避免：

```text
3D 图标、人物、拟物化数据库、复杂渐变、过多阴影、彩虹色、长段落文字、无法编辑的截图。
```

优先使用：

```text
圆角矩形 + 清晰箭头 + 少量图标 + 可读的标签 + 数据来源/范围脚注。
```

## 4. 若需要手工重绘：流程图提示词

下面提示词可用于 draw.io / Figma 的人工绘制参考，也可以提交给图像生成模型生成草图后再人工重绘。**最终论文图应以可编辑矢量图为准。**

### 图 1：系统架构图提示词

```text
请绘制一张学术论文风格的横向系统架构图，白色背景、简洁扁平矢量风格、16:9、中文标签、深蓝主文字。

从左到右绘制：
文档（PDF/DOCX/Markdown）和 Wiki 页面，汇入“C1 声明抽取”；
C1 输出 claim 的 subject、predicate、value、qualifiers、quote；
之后分成“精确候选：same ClaimKey”和“语义 fallback：未覆盖 chunk + HybridSearch”两条通道；
两条通道汇入“C2 级联裁决：保守规则 + grounded LLM”；
输出“Raw Conflict：chunk-pair evidence，不直接治理”；
Raw Conflict 向下/向右进入“C4 DisputedFact：按 fact anchor 聚类，sources + values + members”；
随后依次为“C4.6 Winner Proposal：all-source metadata，advisory only”、
“C4.7 Adoption：explicit snapshot，winner 保留 / loser disable”、
“C4.8 Reopen：durable record，precise re-enable”。

底部绘制一条浅灰色持久化层，包含 claims、conflict_detection_runs、knowledge_conflicts、disputed_facts、durable winner adoptions。
用红色醒目文字标出：proposal 不等于 adoption；adoption 不等于 deletion；reopen 不等于 automatic re-adoption。
使用蓝、青绿、橙、紫、红的有限色板，不要人物、不要照片、不要 3D。
```

### 图 2：事实级聚类与生命周期提示词

```text
绘制一张横向、白底、学术论文风格的流程图，展示三个版本文档如何从 raw pair conflicts 变成一个可撤销的事实级治理动作。

左侧纵向排列三个来源卡片：V1 来源，100 元，issuer A、V1；V2 来源，150 元，issuer A、V2；V3 来源，200 元，issuer A、V3。
中间显示三个红色小卡片：r12 V1↔V2、r13 V1↔V3、r23 V2↔V3；所有卡片箭头汇入一个蓝色大卡片“一个 DisputedFact”，其中列出 claim key、sources=3、candidate values=100/150/200。
右侧是青绿色“C4.6 Proposal”：检查所有来源的 issuer/date/version，唯一严格最大为 V3，仅 advisory；再向下连接橙色“Explicit Lifecycle”：adopt 仅禁用 V1/V2、写 durable record、reopen 精确恢复 V1/V2。
底部红色 fail-closed 卡片写：metadata missing / issuer mismatch / tie → no proposal → HTTP 409 / no mutation。
突出“局部 A/B 方向不直接等于全局 winner”，不要使用人物或装饰性照片。
```

### 图 5：Fail-closed 状态机提示词

```text
绘制一张横向的有限状态机图，白底、论文风格、中文/英文混排标签。

初始状态为蓝色 Pending DisputedFact（raw members pending，chunks enabled）；
连接一个青绿色菱形判断“所有 sources metadata 一致且唯一严格最大？”；
Yes 分支到青绿色 Advisory Proposal（winner + version + snapshot，无副作用）；
之后连接橙色菱形“显式 adoption，snapshot/topology 仍匹配？”；
Yes 分支到紫色 Adopted（winner enabled，loser disabled，durable record）；
从 Adopted 向下到橙色菱形“显式 reopen，active record/targets 匹配？”；
Yes 分支到蓝色 Reopened（raw→pending，record→revoked，targets re-enabled），再用虚线回到 Pending。
第一处 metadata 判断的 No 分支到红色 No Proposal（abstain，无副作用）。
两个 action 判断的 No / stale / partial 分支都汇入红色框“HTTP 409 · no mutation”。
用清晰箭头、圆角矩形、菱形判断框；强调红色 fail-closed 路径；不要 3D、不要图标堆叠、不要人物。
```
