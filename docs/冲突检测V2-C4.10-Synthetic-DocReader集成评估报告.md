## 1. 目的与主张边界

本评估解决的是一个狭窄的工程问题：C4.6/C4.7/C4.8 在此前的 Markdown manual-ingest controlled 场景之外，能否通过真实的文件上传接口处理二进制 PDF/DOCX，并进入同一条异步冲突治理链路。

验证链路为：

```text
multipart HTTP file upload
→ DocReader
→ Asynq document processing
→ claim extraction
→ C2 cascade
→ raw knowledge_conflicts
→ C4 DisputedFact clustering
→ C4.6 global winner proposal
→ C4.7 explicit adoption
→ C4.8 durable reopen
```

本报告**可以**支持以下说法：

```text
在一个无私有数据的受控 PDF/DOCX fixture 上，WeKnora 的真实 HTTP、DocReader、Asynq、PostgreSQL 和配置模型
可以完成文件入口到 explicit winner lifecycle 的集成运行；metadata tie、跨 issuer 与 date/version direction
不一致均按 fail-closed policy 处理。
```

本报告**不可以**支持以下说法：

```text
真实业务文档准确率、真实 PDF/DOCX 跨格式事实聚类泛化、人工审阅准确率、真实用户工时节省、
provider RNG seed control、或现实 authority hierarchy 语义。
```

## 2. Fixture 与运行约束

fixture v2 由 `scripts/experiments/generate_docreader_fixture.py` 确定性生成：

| 部分 | 文档格式 | 内容与目的 |
|---|---|---|
| 核心 lifecycle corpus | 9 份 DOCX | 每份仅含一条已验证的中文数值事实：`国内出差餐费补贴每日标准为 <value> 元。` |
| PDF ingress smoke | 1 份 PDF | 一份独立、ASCII 英文单事实文件；只验证 PDF → DocReader → claim 入口 |
| metadata | scenario `title` | 显式 issuer / effective date / version 标签；file runner 保留扩展名并追加不参与 C3 解析的稳定文档标识，避免 metadata tie 同名上传冲突 |

核心 DOCX matrix 包含：

1. **ordered triplet**：同 issuer、V1/V2/V3，乱序上传 V2→V1→V3，V3 是唯一严格最大来源；
2. **cross issuer**：有同一数值事实冲突，但 issuer 不同，必须无 proposal；
3. **date/version disagreement**：同 issuer，但日期与版本号方向相反，必须无 proposal；
4. **metadata tie**：同 issuer、相同日期/版本号但数值不同，必须无 proposal。

所有实验均创建临时 KB。C4.7/C4.8 的 chunk disable/re-enable 只发生在这些临时 KB 内。

## 4. 发现并修复的 fixture / runner 问题

### 4.1 混合格式英文句式的 claim-key drift

初版 fixture 将相同英文额度句放入 PDF/DOCX。真实模型运行中，V1 被归一为：

```text
国内发票融资 / 单笔最高融资限额
```

而 V2/V3 被归一为：

```text
国内发票融资 / 单张上限
```

因而产生 `fuzzy_slot`、`document_singleton` 与 `claim_key` 三种 anchor，而不是安全地强行合为一个事实。此行为表明系统没有把语义相近但 schema drift 的 claim 冒险视为 exact key。

修复不是放宽 C4 聚类规则，而是将核心 policy/lifecycle fixture 改为已有 C4 exact regression 使用的中文单事实句式，并将跨格式 PDF 测试降为独立 ingress/claim smoke。

### 4.2 metadata tie 的同名文件拒绝

初版 tie case 的两份文件 title 完全相同；file endpoint 按同 KB 文件名拒绝重复上传，导致该 case 未进入检测而显示 `raw=0 / clusters=0`。

`2e1239f` 修复为：当 scenario 未显式指定 `upload_file_name` 时，runner 在保留 issuer/date/version title 与原扩展名的前提下追加：

```text
；文档标识：<document_id>-<short-hash>
```

C3 只解析 allowlisted metadata labels，因此此标识不改变 tie 语义。修复后的 tie case 在 1 次 smoke 和 3 次 independent replicates 中均通过。

## 5. 结论与后续边界

C4.10 synthetic binary fixture 的功能验证已经完成：

```text
DOCX：strict fact cluster / global proposal / adoption / reopen / no-proposal safety
PDF：file ingress / DocReader / claim extraction
```

推荐将它作为：

```text
开发机升级后的 binary-file regression smoke
论文工程实现章节中的 controlled integration evidence
开始真实 corpus 工作前的前置环境检查
```

不应将它作为：

```text
真实 corpus holdout
human-reviewed accuracy result
跨格式 PDF↔DOCX clustering benchmark
外部业务文档泛化结论
```

仍未完成、且与本 fixture 结果相互独立的工作包括：

1. 原 C4.9 formal 15-run matrix 的 historical dead-letter 后验分布记录；
2. 有许可/匿名化的真实 fact-family corpus；
3. development/holdout 严格隔离、双审阅、仲裁、一致性与 95% CI；
4. 多页、复杂版式、扫描件和真实跨格式文本 drift 的独立评估。
