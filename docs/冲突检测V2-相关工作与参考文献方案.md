## 1. 建议的相关工作主线

本文不应把所有“RAG”或“知识图谱”论文堆在一起。建议按研究问题区分为五组：

```text
A. 多源真值发现 / 数据融合
B. Claim verification / NLI / evidence grounding
C. RAG 与 LLM knowledge-conflict evaluation
D. 数据溯源、版本化与可恢复状态
E. Human-in-the-loop 与 fail-closed governance
```

论文的差异化位置应始终保持为：

```text
已有工作通常回答“哪个值更可能为真”或“某条 claim 是否被 evidence 支持”；
WeKnora V2 关注“多来源版本化 KB 中，如何把 chunk-pair conflict 提升为可审计的事实对象，
并把候选 winner 限制为 explicit、snapshot-bound、durable、precise-reopen 的治理操作”。
```

不要声称本文首次发现文档矛盾、首次使用 metadata、首次做版本管理，或首次做 human-in-the-loop；这些说法都过强且不必要。

## 3. 可直接放入正文的 Related Work 初稿

### 3.1 多源真值发现与数据融合

多源数据融合和 truth discovery 关注在多个来源对同一对象提供相互冲突观测时，如何利用 source reliability、值支持度与来源依赖关系推断较可信的值 \cite{yin2008truth,li2016truthsurvey,dong2013datafusion,dong2014knowledgevault}。这类工作通常将目标表述为发现客观 truth 或计算来源可信度，并常假设可从大量对象和来源中学习统计规律。与之不同，本文不学习跨事实的来源全局可靠性，也不将某个文档值直接宣称为现实真值。本文的 winner proposal 是一个受显式 issuer/date/version evidence 限制的版本治理建议；只有经人工/上层工作流显式 adoption 后才产生检索可见性副作用，且该副作用可由 durable record 精确撤销。

### 3.2 Claim verification、证据抽取与自然语言推理

FEVER 与 SciFact 将 claim verification 表述为从文本中检索并选择支持、反驳或不足以判断的证据 \cite{thorne2018fever,wadden2020scifact}。VitaminC 则从 Wikipedia revisions 构造对比式 claim--evidence 样本，强调轻微事实变化下的鲁棒性 \cite{schuster2021vitaminc}。NLI 资源则为 entailment、contradiction 和 neutral 的句对建模提供了基础 \cite{bowman2015snli,williams2018multinli}。本文复用其中“原子 claim + 可定位 evidence”的思想，但研究对象不同：我们处理的是知识库内的多来源版本冲突，而不是为单个外部 claim 判定客观真伪。因而，即使某条 raw pair 被检测为矛盾，其局部方向也不能直接决定全局 winner 或 chunk disable；必须经过 DisputedFact 聚类和全来源 metadata 检查。

### 3.3 RAG、LLM knowledge conflict 与可更新外部知识

RAG 将生成模型与外部可检索的非参数记忆结合，强调知识密集任务中检索、更新和来源可追溯的重要性 \cite{lewis2020rag}。Self-RAG 等工作进一步通过检索与自我批评改善生成质量和事实性 \cite{asai2024selfrag}。ConflictBank 则系统化研究 LLM 内部知识、检索上下文和两者交互下的 misinformation、temporal 与 semantic conflicts \cite{su2024conflictbank}。本文不提出新的生成模型或端到端 QA benchmark；它位于 retrieval/generation 之前，关注 document-side conflict governance：把已检测的冲突持久化、聚类、proposal，并以 fail-closed 协议约束可能影响检索的动作。

### 3.4 公开 temporal-update 与 claim--evidence transfer

WikiFactDiff 将两个 Wikidata 快照之间的原子事实变化组织为带 verbalization template 的更新实例 \cite{ammarkhodja2024wikifactdiff}；VitaminC 则提供 Wikipedia revision 派生的对比式 claim--evidence 证据 \cite{schuster2021vitaminc}。二者可作为外部 transfer 的补充，但不能替代本文的版本治理安全评测：WikiFactDiff 的两快照 adapter 只能检验 public temporal fact 与派生 snapshot metadata 下的 two-source advisory proposal，而不提供 native document-header、multi-authority abstention 或 lifecycle action labels；VitaminC 则只能检验 claim--evidence conflict transfer，而不是 document-version winner governance。正式结果完成前，此段只作为 evaluation design，不作为已完成实验证据。

### 3.5 数据溯源、版本化与人机治理

数据 provenance 研究强调输出与其来源、派生过程之间的可追溯关系 \cite{buneman2001whywhere}。本文将这一思想落实到 conflict governance：每条 claim 保留 quote，DisputedFact 保留 raw members 与 source metadata snapshot，adoption 保留被影响的 chunk/knowledge IDs，reopen 不根据当前猜测恢复，而只根据 durable record 精确恢复。与此同时，Human-AI interaction 指南强调系统在不确定时应限制服务范围、说明行为原因并支持用户纠错 \cite{amershi2019guidelines}。本文不报告 UI user study，而是以 explicit-only、HTTP 409 stale guards、abstention 和 precise reopen 将这些原则具体化为后端协议。
