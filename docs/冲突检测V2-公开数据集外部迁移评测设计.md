# 冲突检测 V2：公开数据集外部迁移评测设计（计划）

> 状态：**WikiFactDiff development pair/proposal 已冻结；VitaminC 仍待官方 real test-only archive 的 adapter-defined disjoint plan 与 development smoke。**
>
> 本文定义的是附加的 external-transfer protocol，不改变或重算已冻结的 C4.9/C4.10 controlled synthetic 结论。

## 1. 目的与边界

现有 C4.9/C4.10 已证明受控事实拓扑上的 lifecycle integration 与 fail-closed policy。为了增加输入文本与事实更新来源的外部性，本阶段增加两种公开 benchmark transfer：

1. **WikiFactDiff**：公开 Wikidata 两个时间快照之间的原子事实更新；
2. **VitaminC real split**：公开 Wikipedia revision 派生的 claim--evidence 支持/反驳实例。

这不是把公开数据“灌入”现有 synthetic 表格，更不是把不同任务拼成一个总体准确率。每个 benchmark 有独立 manifest、split、artifact、指标和论文表格。

明确不声称：

```text
真实企业文档准确率
原生 PDF/DOCX 文档解析准确率
原生文档标题/页眉 metadata extraction accuracy
人类审核准确率或工时节省
多 authority hierarchy 的泛化
端到端 RAG / QA answer correctness
provider RNG seed-controlled 因果结果
```

## 2. 数据集选择

### 2.1 WikiFactDiff：时序事实更新与两快照 proposal transfer

- 论文与发布页：[WikiFactDiff, LREC-COLING 2024](https://aclanthology.org/2024.lrec-main.1532/)。
- 上游项目：[Orange-OpenSource/WikiFactDiff](https://github.com/Orange-OpenSource/WikiFactDiff)。
- 官方 release 描述两个 Wikidata 快照（2021-01-04 与 2023-02-27）的 subject--relation--object 事实变化，并给出 verbalization template。
- adapter 使用 release 的原始 `update_prompt` 与 object label，不调用额外 LLM 重新改写文本。

上游构建代码使用 `keep`、`learn`、`forget`、`ignore`，而当前 Hugging Face dataset card 将发布后的等价决策描述为 `static`、`new`、`obsolete`。adapter 接受两套显式词表，并把实际观测到的 object decision 计入 `source_manifest.json`；未知词一律不猜测。本 protocol 只接受：

| 子任务 | 严格结构条件 | Gold 映射 |
| --- | --- | --- |
| Pair conflict detection | `is_replace=true`，且恰好一个 `forget/obsolete` 和一个 `learn/new` | obsolete/forget → new/learn 是 conflict 正例 |
| Pair no-conflict control | 非 replacement group 中至少一个 `keep/static` object；按 ID/label 固定选一个 | 同一个 static/keep fact 写入两份文本，是窄 no-conflict control |
| C3/C4.6 proposal transfer | 上述 replacement 正例 | 新快照为 expected advisory winner |

static/`keep` control 只测“相同原子 statement 不应被报冲突”；它不代表真实文档的完整多事实版本，也不用于 C4.6 abstention 指标。

对于 proposal 子任务，adapter 在**实验 title**（而非正文）中放入：

```text
Publisher: Wikidata
Effective date: <release old/new snapshot date>
Version: <release old/new snapshot date rendered as dotted version>
```

这些 metadata 是从 WikiFactDiff release 的 snapshot provenance **派生**的，不是从原始公共文档 header 抽取的。因为公开 release 只有两个快照，本任务保持真实两 source topology：不伪造第三份副本来凑 C4.9 的三 source lifecycle 前提。因此它只报告：

```text
public temporal fact pair transfer
public two-snapshot C3/C4.6 advisory proposal transfer
exact winner + exact source-count success
```

它不报告 proposal precision、abstention precision、multi-authority safety、C4.7 adoption 或 C4.8 reopen。后四项仍由已冻结的 C4.9/C4.10 controlled matrix 支撑。

### 2.2 VitaminC real split：C1/C2 claim--evidence conflict transfer

- 论文与发布页：[VitaminC, NAACL 2021](https://aclanthology.org/2021.naacl-main.52/)。
- 上游项目与下载说明：[TalSchuster/VitaminC](https://github.com/TalSchuster/VitaminC)。
- 仅使用上游单独发布的 **real** archive（`vitaminc_real.zip`）；不把 combined `vitaminc.zip` 当作 real-only 证明，也不混入 `synthetic` member。
- 官方 dedicated `vitaminc_real.zip` 在实践中是 **real test-set 包**：成员仅为 `vitaminc_real/test.jsonl`（外加 LICENSE/README），没有 native `train.jsonl` / `dev.jsonl`。
- 因此 VitaminC development/holdout 是 adapter 对该唯一 `test.jsonl` 的确定性互斥切分：每个 label 先取 `selection_rank` 前缀作为 development，再取随后未使用 family 作为 holdout。这不是官方 VitaminC train/dev/test split，论文中必须写成 adapter-defined partition of the official real test member。
- 上游 `REFUTES` 映射为 expected conflict，`SUPPORTS` 映射为 expected no-conflict；`NOT ENOUGH INFO` 与未知标签不进入本实验。

每条 benchmark record 被转换为两份 manual-text document：一份只含 claim，一份只含 evidence。这个转换测试的是 WeKnora 的 claim extraction/candidate/adjudication 能否迁移到公开的 claim--evidence 模式，不是原 benchmark 的完整 fact-verification task。

因此 VitaminC 绝不添加 C3/C4.6 title metadata、winner label、adoption 或 reopen。若系统在该数据上报出了 pair conflict，只能称为：

```text
public claim--evidence conflict-transfer detection
```

不能称为版本治理成功率。

## 3. 数据许可、隐私与仓库策略

- WikiFactDiff 的上游项目代码使用 MIT，而当前 Hugging Face dataset card 标注 release 为 CC BY-SA 4.0；实际使用的 release、config、revision、输入 SHA-256 必须逐次记录在 `source_manifest.json`，并在投稿前再次核对数据发布条款。
- VitaminC 的 `DATA_LICENSE` 说明其注释包含 Wikipedia material，并指向适用 Wikipedia terms / CC BY-SA 3.0 fallback。下载、派生文本、发布 artifact 前必须保留 attribution 并核对当前条款。
- 原始 archive、download cache、生成的 public text、临时 KB artifact 和含源码句子的 CSV 均放在例如 `$HOME/weknora-public-data/` 的仓库外目录；不提交到 Git。
- Git 中仅保留 adapter、运行器、无原文的设计文档和可复现命令。

## 4. 防泄漏与预注册选择

每个 adapter 均执行以下静态步骤，期间不访问 WeKnora 服务、模型、Asynq、Docker 或数据库：

1. 验证 source schema、文本长度、标签、release member 和严格结构条件；
2. 用 hash-based `selection_seed` 进行确定性排序；
3. 固定 fact-family ID，保证 development/holdout 不复用同一 canonical source pair；
4. 记录 source SHA-256、scan 是否完整、过滤数、可用样本数、选择 rank；
5. 生成可直接交给 `run_claims_eval.py` 的 scenario 和 pair manifest。

推荐初始 plan：

| 数据集 | Development | Holdout | 说明 |
| --- | ---: | ---: | --- |
| WikiFactDiff pair | 10 replacement + 10 static/keep control | 30 + 30 | C1/C2 public temporal pair transfer |
| WikiFactDiff proposal | 10 replacement | 30 replacement | C3/C4.6 two-snapshot proposal transfer |
| VitaminC real | 10 REFUTES + 10 SUPPORTS | 30 + 30 | C1/C2 claim--evidence transfer |

上表是预先确定的**事实家族**数量，不是 provider 调用数量。若 `--max-*-records` 截断输入，source manifest 会标为 `partial_smoke_only`；这种输出只能用于通路检查，不能作为正式 holdout。

## 5. 执行顺序

### 5.1 生成公开计划

```bash
cd ~/weknora
PUBLIC_ROOT="$HOME/weknora-public-data"
mkdir -p "$PUBLIC_ROOT"
chmod 700 "$PUBLIC_ROOT"

# WikiFactDiff：adapter 默认固定在上游 revision
# bb17ffbff7b2d28e4cd12e251af3db50d7fa18ea，并使用 card 标为
# recommended 的 20210104-20230227_legacy config；首次缺少依赖时安装。
python3 -m pip install --user datasets

make experiment-public-wikifactdiff-plan \
  PUBLIC_OUTPUT="$PUBLIC_ROOT/wikifactdiff-20210104-20230227-legacy-v1" \
  DEV_PER_LABEL=10 \
  HOLDOUT_PER_LABEL=30 \
  PUBLIC_VARIANT=c2-rules
```

VitaminC 从上游 README 的 release link 下载后：

```bash
# 使用上游单独发布的 real-only archive；combined vitaminc.zip 不用于本 protocol。
VITAMINC_ZIP="$PUBLIC_ROOT/vitaminc_real.zip"
curl -L --fail --retry 3 \
  -o "$VITAMINC_ZIP" \
  "https://github.com/TalSchuster/talschuster.github.io/raw/master/static/vitaminc_real.zip"

# 不显示原文，仅查看全部 member 路径。官方 dedicated real archive 实测只有 test.jsonl。
unzip -Z1 "$VITAMINC_ZIP"

make experiment-public-vitaminc-plan \
  VITAMINC_DEVELOPMENT="$VITAMINC_ZIP" \
  VITAMINC_HOLDOUT="$VITAMINC_ZIP" \
  PUBLIC_OUTPUT="$PUBLIC_ROOT/vitaminc-real-v1" \
  DEV_PER_LABEL=10 \
  HOLDOUT_PER_LABEL=30 \
  PUBLIC_VARIANT=c2-rules
```

如果 VitaminC archive member 自动识别失败，读取 `unzip -Z1` 返回的**路径名**后，以 `VITAMINC_DEVELOPMENT_MEMBER=...` 和 `VITAMINC_HOLDOUT_MEMBER=...` 显式传入。不要上传 archive 或粘贴其正文到对话。

### 5.2 Development smoke 与 protocol freeze

以 WikiFactDiff 为例：

```bash
WFD_ROOT="$PUBLIC_ROOT/wikifactdiff-20210104-20230227-legacy-v1"

make experiment-public-pair-dry-run \
  PUBLIC_MANIFEST="$WFD_ROOT/pair_eval_manifest.json" \
  SPLIT=development \
  PUBLIC_MAX_CASES=10

make experiment-public-pair-eval \
  PUBLIC_MANIFEST="$WFD_ROOT/pair_eval_manifest.json" \
  SPLIT=development \
  PUBLIC_MAX_CASES=10 \
  PUBLIC_OUTPUT="$WFD_ROOT/runs/pair-development-smoke"
```

Development 可用于检查：source adapter、文本长度阈值、claim-key drift、fallback、任务死信和 API/Asynq 稳定性。若要修改 adapter、variant、prompt、模型或过滤规则，必须：

1. 在 development 中完成修改；
2. 生成新的 versioned source manifest；
3. 清楚保留旧 plan；
4. 在未运行的 holdout 上重新执行。

不可根据 holdout 成败修改 selection 或静默删除 case。

### 5.3 Holdout 与稳定性 slice

Development protocol 冻结后，先对完整 holdout 执行一次：

```bash
make experiment-public-pair-eval \
  PUBLIC_MANIFEST="$WFD_ROOT/pair_eval_manifest.json" \
  SPLIT=holdout \
  PUBLIC_REPLICATES=1 \
  PUBLIC_OUTPUT="$WFD_ROOT/runs/pair-holdout-r1"
```

如果需要服务运行稳定性证据，使用 adapter 预先固定 rank 的前 10 个 holdout families，另建不与完整 holdout 池化的 slice：

```bash
make experiment-public-pair-eval \
  PUBLIC_MANIFEST="$WFD_ROOT/pair_eval_manifest.json" \
  SPLIT=holdout \
  PUBLIC_MAX_CASES=10 \
  PUBLIC_REPLICATES=3 \
  PUBLIC_OUTPUT="$WFD_ROOT/runs/pair-holdout-stability-r3"
```

`replicate` 表示 fresh temporary KB 的独立服务执行，**不表示** provider RNG seed-controlled trial。

## 6. 评分与完整性规则

`run_public_pair_eval.py` 在启动 case 前，先要求同一 shell 中存在 `WEKNORA_EXPERIMENT_TEMPLATE_KB`（或显式 `--template-kb-id`），并运行一次已有的只读 `run_claims_eval.py --check --check-db`。若这个 preflight 失败，runner 写入 `<output>/service_preflight.log` 并停止，不会把同一个环境错误扩散成一批 `UNEVALUABLE` case。

每个通过 preflight 的 case 调用已有真实链路：

```text
public HTTP API
→ temporary KB
→ manual processing task
→ claim extraction
→ conflict detection
→ PostgreSQL read-only artifact export
```

### 6.1 Pair-level classification

| Gold | observed document pair conflict | 计数 |
| --- | --- | --- |
| conflict | yes | TP |
| conflict | no | FN |
| no conflict | yes | FP |
| no conflict | no | TN |

`run_claims_eval.py` 返回 `2` 可能只是 gold assertion 未命中；只要 `manifest.json` 为 `completed*` 且必要 JSON artifact 完整，该 case 仍是**可评测的错误**（FP/FN），而不是 infrastructure failure。

缺 `manifest.json`、`metrics.json`、`conflict_document_pairs.json`，非 `completed*` 状态，或异常 exit code 则为 `UNEVALUABLE`。UNEVALUABLE 绝不能计为 TN：

```text
headline precision / recall / accuracy = null  （若存在任一 unevaluable observation）
conditional_*                           = 仅在可评测子集上显示
```

### 6.2 Fact-family strict-all-replicates

多 replicate 的主要指标单位为 fact family，而不是把 3 次服务执行误记为 3 个独立事实：

- conflict family：所有 replicate 都命中才计 TP；任一遗漏计 FN；
- no-conflict family：所有 replicate 都安静才计 TN；任一误报计 FP；
- 缺任一 artifact：计 UNEVALUABLE。

### 6.3 WikiFactDiff proposal transfer

proposal manifest 额外检查：

```text
detector scenario status == completed（pair / cluster / winner assertions 均通过）
exactly one observed proposal
winner_document == expected new snapshot
proposal source_count == 2
```

它只报告 `exact winner + source-count success rate`。没有 public no-proposal/multi-authority 负例，就不能把这一成功率写成 C4.6 precision 或 safety generalization。

### 6.4 运行 artifact

每个 public pair eval 输出：

```text
<run>/
├── manifest.json
├── execution_results.json / .csv
├── fact_family_results.json / .csv
├── metrics.json
├── report.md
└── replicates/<case>/replicate-XX/detector/
```

`metrics.json` 还记录 dead-letter aggregation、claim/raw-conflict count 和 cascade operational shape。公共 transfer corpus 不是 C2 级联消融，因此不能用其 aggregate token/call 数替代已冻结的 C2 ablation。

若发现旧版 public-pair summary 的 `cascade.totals` 全为零，而 immutable per-case `execution_results.json` 中保存的 `cascade.totals` 有值，应使用 `resummarize_public_pair_eval.py --apply` 做只读后验重汇总，而不是重跑 detector。该工具会先备份旧 summary，保留原始 case artifacts，且不会调用服务或模型。

## 7. 投稿中可用的写法（仅在真实结果完成后）

可以写：

> We additionally evaluated transfer on two public, adapter-defined benchmarks. WikiFactDiff provides public temporal fact changes between two Wikidata snapshots; VitaminC supplies real Wikipedia-revision-derived claim--evidence examples. We report these results separately from controlled synthetic lifecycle metrics and retain dataset-specific scope constraints.

必须同时写清：

> WikiFactDiff title metadata were derived from release-level snapshot provenance, and its two-snapshot proposal subset does not test multi-authority abstention or lifecycle actions. VitaminC evaluates claim--evidence conflict transfer, not document-version governance. Neither evaluation estimates enterprise-document or human-review accuracy.

在有完整实际结果前，不把此设计或预定 sample count 写成已完成的实验；不修改当前 C4.9/C4.10 frozen 数字。
