# 冲突检测 V2：C4.10 扩展 Synthetic Policy Corpus 与事实家族评估设计

> 状态：已实现脚本与静态验证；等待 development / holdout 的真实服务运行。
>
> 最近更新：2026-09-15（Asia/Shanghai）
>
> 范围：研究原型的 controlled policy evaluation；不替代真实语料与双审阅。

---

## 1. 目的

已有 C4.10 `docreader_fixture` 证明了 PDF/DOCX 文件入口与一个小型 DOCX lifecycle matrix 可以运行，但只有 4 个事实家族，适合作为回归 smoke，不足以系统覆盖 proposal / abstention policy。

本阶段新增一个**确定性生成**的 synthetic corpus，用于在不依赖低质量或私有真实文档的前提下，扩大以下受控条件的覆盖：

```text
同 issuer 的唯一全局 winner
上传顺序与 metadata 顺序不一致
仅 date / 仅 version 的可比较正例
cross issuer
mixed issuer triplet
metadata missing
date/version direction disagreement
metadata tie
date interval overlap
```

它验证的是：系统是否按预先声明的 policy 执行、拒绝不安全动作，以及各 baseline 在同一 policy corpus 上的行为。

---

## 2. 非目标与论文边界

本语料不会声称：

```text
真实业务文档准确率
真实 PDF↔DOCX 跨格式聚类泛化
真实 authority hierarchy 的正确性
人工审阅准确率或 Cohen's kappa
provider RNG seed control
```

它不是让 LLM 自动编写文档、再用同一个 LLM 给自己打分。文档、metadata、预期 winner/no-proposal、冲突对和 split 都由确定性脚本预先定义，并写入 manifest。它仍是**controlled synthetic policy corpus**，不能取代后续真实 holdout。

---

## 3. 生成器

入口：

```text
scripts/experiments/generate_winner_policy_corpus.py
```

默认生成：

```text
12 development fact families
12 holdout fact families
12 adopt_reopen positives
12 no_proposal negatives
64 个虚构 DOCX 文件
```

默认 24 families 是为了先控制 development/holdout 的运行成本；若要达到 30-family controlled pilot，可显式使用
`DEV_FAMILIES=15 HOLDOUT_FAMILIES=15`。每个 split 支持 4–20 families，避免一次生成无意间造成过大的模型调用量。

每个文件只有一个受控事实，例如：

```text
国内出差餐费补贴每日标准为 100 元。
```

development 与 holdout 使用不重复的中文事实 subject；同一 family 内则保持完全稳定的句式，避免把 C4 policy 测试混入无关的 claim schema drift。每个 case 使用新的临时 KB，因此不同 family 的同类政策不会在同一 KB 中互相污染。

输出目录包含：

```text
corpus.json
fact_family_catalog.csv
generator_manifest.json
README.md
docs/<split>/<case>/*.docx
```

每个生成文档带 SHA-256，后续 file runner 会在上传前重新核验，防止生成文件被静默修改。

## 4. Split 与 case topology

### 4.1 Development / holdout

- split 单位是 `fact_family_id`，不是 raw conflict 或单份文档；
- development / holdout 不共享 document path；
- development / holdout 不复用生成器的事实 subject；
- `build_winner_corpus_matrix.py` 继续拒绝 fact family 或 document path 跨 split 泄漏；
- generated scenario、matrix 和 reviewer CSV 现在都携带 `fact_family_id`、`split`、`case_type`。

该隔离只保证受控 policy setup 的结构隔离；相同的简单句法框架是刻意保留的。因此 holdout 结果只能称为**未参与调试的 controlled policy holdout**，不能称为外部语义泛化。

### 4.2 Positive topology

每个 `adopt_reopen` case：

```text
3 个同 issuer sources
同一事实、3 个不同值
唯一严格较新的 metadata source
expected winner 在 case 内
adoption_cycles = 1
```

生成器覆盖：

```text
date + version 都递增
date + version 都递增但上传乱序
date-only 严格递增
version-only 严格递增且上传乱序
```

### 4.3 Negative topology

每个 `no_proposal` case 仍明确要求 raw conflict；它不是“随便两份无关文档”。生成器覆盖：

```text
cross_issuer_pair
mixed_issuer_triplet
metadata_missing_triplet
date_version_disagreement_pair
metadata_tie_pair
date_interval_overlap_pair
```

`metadata_tie_pair` 的 title 可保持相同。file runner 会自动追加一个 C3 忽略的稳定 `文档标识` 字段，避免 HTTP file API 因同名拒绝第二份来源。

## 5. 执行协议

生成 corpus：

```bash
CORPUS_ROOT="$HOME/weknora-private-corpus/synthetic-policy-v1"

make experiment-c410-synthetic-corpus \
  OUTPUT="$CORPUS_ROOT"
```

物化 matrix：

```bash
make experiment-c410-plan \
  CORPUS="$CORPUS_ROOT/corpus.json" \
  OUTPUT="$CORPUS_ROOT/plan"
```

Development 只运行一次，用于发现格式、metadata 或脚本问题：

```bash
python3 scripts/experiments/run_winner_lifecycle_eval.py \
  --matrix "$CORPUS_ROOT/plan/winner_lifecycle_matrix.development.json" \
  --replicates 1 \
  --output-dir "$CORPUS_ROOT/runs/development-r1"
```

只有在以下内容冻结后才运行 holdout：

```text
代码 commit
模型/KB 配置
metadata policy
case generator
baseline scorer
```

Holdout 建议运行 3 次独立 replicate：

```bash
python3 scripts/experiments/run_winner_lifecycle_eval.py \
  --matrix "$CORPUS_ROOT/plan/winner_lifecycle_matrix.holdout.json" \
  --replicates 3 \
  --output-dir "$CORPUS_ROOT/runs/holdout-r3"
```

每个 child run 均通过真实 HTTP API、真实 DocReader、Asynq、PostgreSQL 和配置模型。当前 C4.9 driver 会把 `dead_letter_count != 0` 视为 case failure。

若 holdout matrix 中任一 detector artifact 缺失、failed 或不满足 assertion，整次 holdout 只可标为**incomplete**：

```text
headline proposal precision/recall = null
fact-family scorer 默认拒绝评分
保留原 artifact
修复基础设施后用新的 run ID 重跑完整 holdout matrix
```

不能把 failed negative 的空 winner list 当成一个正确 no-proposal，也不能把补跑的单个 case 静默拼回原 holdout。

## 6. 事实家族与 baseline scorer

入口：

```text
scripts/experiments/score_winner_fact_families.py
```

运行：

```bash
make experiment-c410-fact-eval \
  MATRIX_RUN="$CORPUS_ROOT/runs/holdout-r3"
```

输出位于：

```text
<MATRIX_RUN>/fact_family_evaluation/
├── baseline_policy_metrics.json
├── execution_results.json
├── execution_results.csv
├── fact_family_results.json
├── fact_family_results.csv
└── report.md
```

比较方法：

| 方法 | 定义 | 目的 |
|---|---|---|
| `c46_global_proposal` | detector artifact 中实际观察到的 C4.6 proposal | 系统方法 |
| `latest_upload` | 无条件选择 scenario 最后上传的来源 | 排序/上传时间启发式 |
| `date_only` | 忽略 issuer/version，仅选唯一严格最新日期区间 | 单信号 baseline |
| `version_only` | 忽略 issuer/date，仅选唯一严格最大版本号 | 单信号 baseline |
| `raw_c3_local_vote` | 每条有方向 raw C3 suggestion 投一票；平票/无票 abstain | 局部 pair 方向 baseline |

计分规则：

```text
positive：仅 expected winner 为 TP；错误 winner 同时记 FP + FN；abstain 记 FN
negative：abstain 为 TN；任何 proposal 为 FP + unsafe action
```

输出包含两个口径：

1. **execution-level**：每个 case × replicate；
2. **fact-family strict-all-replicates**：同一 family 的所有 replicate 都正确，才记为正确。

后者是主口径，避免把同一 family 的 3 次独立运行误当成 3 个独立事实样本。scorer 默认会拒绝缺失 replicate、重复 replicate 或失败 execution；只有明确传入 `--allow-failed` 时才输出失败诊断。报告同时列出每个 baseline 的 replicate prediction stability、raw/cluster 形状和 cascade 成本聚合。scorer 不导出正文；
但对真实 corpus 仍可能包含 document ID、metadata 和 artifact 路径，因此应保留在私有 matrix run 目录，不提交 Git。

## 7. 完成标准与下一阶段

本阶段达标条件：

```text
- 生成器输出通过 corpus split/path leakage guard；
- development matrix 可用于调试；
- holdout matrix 在冻结后真实运行；
- fact-family scorer 输出 C4.6 与四个 baseline 的 policy metrics；
- 全部 dead-letter gate 为零；
- 明确报告 synthetic scope 与 failure cases。
```

达标后，可以把论文的 evaluation 部分升级为：

```text
C1 extraction audit
C2 cost ablation
C4 clustering
C4.6/C4.7/C4.8 controlled lifecycle
C4.10 binary file integration
expanded synthetic development/holdout policy evaluation + baselines
```

若后续希望主张真实业务文档效果，仍需单独建立有许可/匿名化真实 corpus、双审阅与独立真实 holdout；它不是本阶段的替代品。
