## 1. 背景与目标

### 1.1 要解决的问题

现有 M3 冲突检测以 **chunk 对**为基本单位，粗筛依赖整块 embedding 相似度
（`knowledge_conflict.go: coarseFilterBySearch`，HybridSearch 阈值 0.4 / top-8）：

- 相似 ≠ 同一事实：同主题不同侧面误配对（烧 LLM），跨表述真冲突漏召回（S1）；
- 一个 chunk 含十几条事实，LLM 只能报"这两块矛盾"，定位不到声明级（S2）；
- wiki 页面内容完全不参与冲突审查（S7 的检测半边）。

### 1.2 C1 交付物

1. **claims 表**：文档 chunk 与 wiki 页面统一声明化的持久索引；
2. **声明抽取服务**：摄取后异步抽取原子声明，幂等、可重抽、剔除机器管理区；
3. **双源触发**：文档摄取完成触发 + 用户编辑 wiki 触发（防抖、EditSource 过滤）；
4. **冲突粗筛改造**：声明键配对为主通道、HybridSearch 兜底的双通道候选生成；
5. **生命周期联动**：文档/chunk/wiki 页删除或禁用时清理对应 claims。

### 1.3 非目标（明确不做，留给后续里程碑）

- 不改 LLM 裁决逻辑与成本结构（C2 级联验证器）；
- 不引入文档元数据/版本判定（C3）；
- 不做冲突聚类与 wiki 写回（C4）；claims 表仅为其预留字段；
- 不做全库巡检调度（C6）；本期只保证巡检所需的索引可查询。

## 2. 总体架构

```
┌─ 文档源 ────────────────────────────────────────────────────────┐
│ 上传解析完成 (knowledge_process.go)                              │
│   └→ enqueue claim:extract {source_type: chunk, knowledge_id}   │──┐
└──────────────────────────────────────────────────────────────────┘  │
┌─ Wiki 源 ───────────────────────────────────────────────────────┐  │
│ UpdatePage 且 EditSource==user 且发生真实内容变更 (version bump) │  │
│   └→ 防抖登记 → enqueue claim:extract {source_type: wiki_page}  │──┤
└──────────────────────────────────────────────────────────────────┘  │
                                                                      ▼
                                            ┌──────────────────────────────┐
                                            │ ClaimExtractService.Handle   │
                                            │ 1. 载入源内容(chunks/页面)    │
                                            │ 2. 机器管理区剔除(wiki)       │
                                            │ 3. LLM 批量抽取原子声明       │
                                            │ 4. 键规范化 claim_key         │
                                            │ 5. 幂等落库(替换式 upsert)    │
                                            └──────────────┬───────────────┘
                                                           ▼
                                                    ┌──────────────┐
                                                    │  claims 表    │
                                                    │ (键索引)      │
                                                    └──────┬───────┘
                                                           ▼
                                     ┌──────────────────────────────────────┐
                                     │ 冲突粗筛(改造后 knowledge_conflict.go)│
                                     │ 主通道: 同 claim_key 跨源配对          │
                                     │ 兜底: HybridSearch(保留现有路径)      │
                                     └──────────────────────────────────────┘
```

设计原则：
- **旁路增量**：claims 是纯新增子系统，KB 开关关闭时所有行为与 V1 完全一致；
- **幂等可重放**：任何一次抽取失败/重试/重抽,不产生重复行、不留脏数据；
- **双源同构**：chunk 与 wiki 页面产出同一张表、同一套键空间,后续配对无需区分处理。

## 3. 数据模型

### 3.1 `claims` 表（migrations/versioned/000085 + migrations/sqlite/000006）

```sql
-- Migration: 000085_claims
-- Atomic claims extracted from document chunks and wiki pages (C1).
-- One row = one atomic factual claim anchored to its source span.
CREATE TABLE IF NOT EXISTS claims (
    id                VARCHAR(36) PRIMARY KEY,
    tenant_id         BIGINT       NOT NULL,
    knowledge_base_id VARCHAR(36)  NOT NULL,

    -- 来源锚定（双源）
    source_type       VARCHAR(16)  NOT NULL,             -- 'chunk' | 'wiki_page'
    source_id         VARCHAR(36)  NOT NULL,             -- chunk.id 或 wiki_pages.id
    knowledge_id      VARCHAR(36)  NOT NULL DEFAULT '',  -- chunk 源冗余其所属文档，wiki 源为空
    span_start        INT          NOT NULL DEFAULT 0,   -- 声明在源文本中的字符区间（rune 下标）
    span_end          INT          NOT NULL DEFAULT 0,

    -- 声明四元组
    subject           TEXT         NOT NULL,             -- 原文主体表述
    predicate         TEXT         NOT NULL,             -- 原文属性表述
    value             TEXT         NOT NULL,             -- 原文取值表述
    qualifiers        JSON,                              -- {time,scope,unit,condition,...} 可空

    -- 规范化配对键
    claim_key         VARCHAR(512) NOT NULL,             -- norm(subject) + '@' + norm(predicate)
    value_norm        VARCHAR(512) NOT NULL DEFAULT '',  -- 规范化取值（数值归一/单位归一后）
    value_kind        VARCHAR(16)  NOT NULL DEFAULT 'text', -- 'number'|'enum'|'date'|'text'

    -- 抽取管理
    extractor_version INT          NOT NULL DEFAULT 1,   -- 抽取器版本，支持全量重抽
    extract_batch_id  VARCHAR(36)  NOT NULL DEFAULT '',  -- 一次抽取任务的批次号（替换式 upsert 用）

    created_at        TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_claims_kb_key      ON claims (knowledge_base_id, claim_key);
CREATE INDEX IF NOT EXISTS idx_claims_source      ON claims (source_type, source_id);
CREATE INDEX IF NOT EXISTS idx_claims_knowledge   ON claims (knowledge_id);
CREATE INDEX IF NOT EXISTS idx_claims_tenant      ON claims (tenant_id);
```

设计说明：

| 决策 | 理由 |
|------|------|
| 存原文表述（subject/predicate/value）+ 规范化键（claim_key/value_norm）双份 | 配对走规范化键；LLM 裁决与争议块展示需要原文表述，避免二次回源 |
| `span_start/end` 只存区间不存全文 | 控制表体积（预估 10–30 claims/chunk）；展示时按需回源截取 |
| `value_kind` 预分类 | C2 规则层直判的路由依据（number/enum 走免费比较器） |
| `extract_batch_id` | 替换式 upsert 的实现载体（见 §5.4），天然幂等 |
| `qualifiers` 用 JSON 而非独立列 | 限定词开放集合；C2 只需"完全相同/不相交"判断，无需列级索引 |
| 不加外键约束 | 与仓库现有风格一致（knowledge_conflicts 亦无 FK），删除联动走服务层 |

**claim_key 长度上限 512**：超长主体/属性截断前先做规范化；截断后追加 8 位内容哈希防碰撞。

## 4. 键规范化（claim_key）

配对精度的核心。**本期采用保守规则式规范化**（不引入 LLM 二次归一,不做同义词表——
留作 C2 后的调优项），宁可漏配（HybridSearch 兜底还在），不可错配。

```
norm(s):
  1. Unicode NFKC 归一（全角→半角等）
  2. 去首尾空白；内部连续空白折叠为单个
  3. 英文小写化
  4. 去除包裹性标点（书名号、引号）；保留主体内部的连字符/点号
  5. 中文不分词、不去停用词（保守：避免"报销上限"vs"报销的上限"误合并交给兜底通道）
claim_key = norm(subject) + "@" + norm(predicate)
超长（>500 rune）: 截断 + "#" + sha256(全文)前8位
```

`value_norm` 附加规则：
- `number`：提取数值 + 单位归一（万→10^4、%→小数），格式 `"5000|cny/month"`；
  单位不可识别时保留原样，`value_kind` 降级为 `text`；
- `date`：ISO-8601 归一（"2026年6月" → "2026-06"）；
- `enum/text`：与 norm(s) 同规则。

单位换算表首期只覆盖：中文数量级（万/亿）、百分比、常见货币、时间单位。表驱动,
放 `internal/application/service/claim_normalize.go`,便于扩展与单测。

### 4.1 v1.1 校准补充（来源：抽取质量评估,见评估报告）

编码前置评估（`testdata/claims_eval/`）暴露两类系统性失配,规范化规则据此升级：

1. **括号注释剔除**：`（…）/(…)` 整体移除（英文原名、补充说明不参与匹配）,先于边缘裁剪；
2. **text/enum 值深度归一**（仅用于匹配比较,不改变存储表述）：去助词"的"、去连接词
   （并在/并且/并/且/以及）、去顿号/逗号/间隔号、去肯定情态前缀（必须/须/应当/应/需要/需）、
   去尾部量词（N家/N个/…）；**否定词（不/不得/非/禁止）一律保留**,防语义翻转；
3. **谓词词缀表**：剥离弱语义前缀 {项目,年度,完成,申请,选择,上岗,例行} 与后缀
   {要求,方式,节点}。小词表原则,防过拟合；生产语料复跑时重点观察误合并率；
4. **融合键**：`fused_key = norm(subject) + norm_predicate(predicate)` 作为配对与聚类的
   主比较键,消除主/谓切分边界的任意性（"幽能引擎@原型机测试时间" 与
   "幽能引擎原型机@测试时间" 融合后相等）。带 `@` 的 claim_key 保留用于展示调试；
   claims 表以 fused 形式存储 `claim_key` 列,subject/predicate 原文另列保存。

参照实现与用例：`testdata/claims_eval/evaluate.py`（Go 移植时以其为算法原型,
单测用例矩阵直接取材）。评估结论：合并口径 P=0.934 / R=0.905（门槛通过）,
预埋矛盾对 strict 通道 3/5、+relaxed 4/5,主体同义词类分歧（"报销申请"↔"报销单"）
为声明键通道预期盲区,由 HybridSearch 兜底通道覆盖（§7）。

## 5. 声明抽取服务

### 5.1 服务接口（internal/application/service/claim_extract.go）

### 5.2 任务载荷与队列（internal/types/task.go）

```go
const TypeClaimExtract = "claim:extract"
```

注册点：`internal/router/task.go`（worker mux）、`internal/router/sync_task.go`（同步执行器）。

### 5.3 LLM 抽取

**输入组织**：按源聚批——chunk 源一次任务处理一个 knowledge 的全部启用 chunk，
每次 LLM 调用打包 3–5 个 chunk（控制在 ~6000 rune 内,对齐 conflictContentMaxRunes 经验值）；
wiki 源一次任务处理一个页面（先剔除机器管理区,见 §5.5）。

**输出协议**（严格 JSON,复用 `stripJSONFences` 解析防御）：

```json
{"claims": [{
  "chunk_index": 0,
  "subject": "差旅报销",
  "predicate": "每月上限",
  "value": "5000元",
  "qualifiers": {"scope": "国内出差", "time": "2026-06起"},
  "value_kind": "number",
  "quote": "国内出差每月报销上限为5000元"
}]}
```

- `quote` 是源文本中的**逐字引用**,服务端用它在源中定位 `span_start/end`
  （精确匹配 → 失败则空白折叠后匹配 → 再失败置 0,0 并计数告警指标）；
- 服务端**不信任** LLM 的 value_kind：value_norm 归一失败即降级 text；
- 抽取温度 0.1、MaxTokens 按批内容量动态（约 输入 rune/3）,失败重试 1 次后跳过该批
  （部分成功可接受,批间独立）。

**Prompt 要点**（完整草案见附录 A）：只抽客观事实断言；主观评价/流程描述/示例代码不抽；
每条声明必须自含（主体不得是代词）；qualifiers 尽量填 time/scope/unit/condition 四槽。

### 5.4 幂等：替换式 upsert

```
batchID = uuid.New()
1. 抽取全部成功批 → 构造 []Claim{ExtractBatchID: batchID}
2. 事务内：INSERT 新行 → DELETE WHERE source_type=? AND source_id=? AND extract_batch_id != batchID
```

- 重复触发（重试、手工重抽）结果收敛于最后一次批次,无重复行;
- **部分批失败策略**：若任一 LLM 批失败,该 source 本轮不执行 DELETE（保留旧索引比
  半新半旧更安全）,任务返回错误交给 asynq 重试;
- `extractor_version` 写入当前常量 `claimExtractorVersion`;后续升级抽取 prompt 时
  版本 +1,C6 巡检可按 `extractor_version < current` 挑选待重抽源。

### 5.5 机器管理区剔除器（wiki 源专用）

抽取前对页面 Content 做区域剔除,**这是环路防断的第二道闸**（第一道是 EditSource 过滤）：

```go
// StripMachineManagedBlocks 移除 weknora:dispute 等机器管理标记区。
// 标记规范见里程碑规划 §1.2。基于行扫描的状态机,非正则贪婪匹配,
// 防御嵌套/未闭合标记（未闭合时剔除至文末并计告警指标）。
func StripMachineManagedBlocks(content string) (stripped string, blocks []MachineBlock)
```

首期识别 `<!-- weknora:dispute ... --> ... <!-- /weknora:dispute -->`;
`## 用户补充` 节（M5 反哺产物）**参与**抽取——它是用户贡献的知识,正是需要审查的对象。
返回的 `blocks` 供 C4 写回时复用定位,函数放独立文件便于双方引用。

**span 映射**：剔除改变了字符偏移。抽取在 stripped 文本上进行,落库前通过剔除器返回的
偏移映射表将 span 还原为原文坐标（保证 C4 争议块定位与前端高亮正确）。

## 6. 触发路径

### 6.1 文档源：摄取完成后

挂钩点：`knowledge_process.go` 现有 M3 入队处（第 706 行附近）,顺序调整为：

```go
if kb.IsClaimExtractEnabled() {
    s.enqueueClaimExtractTask(ctx, knowledge)   // 先抽取
}
if kb.IsConflictDetectEnabled() {
    s.enqueueConflictDetectTask(ctx, knowledge) // 后检测（同队列 FIFO,天然后行）
}
```

同队列顺序入队即可获得"先抽取后检测"的弱保证;检测侧仍需容忍 claims 缺失
（降级走 HybridSearch 兜底,见 §7）,不做强依赖。

### 6.2 Wiki 源：用户编辑后（防抖）

挂钩点：`wiki_page.go: UpdatePage` 完成持久化之后。触发条件（三者同时满足）：

1. `NormalizeWikiEditSource(source) == WikiEditSourceUser`；
2. 本次调用发生了**真实内容变更**（复用 UpdatePage 既有的 contentChanged 判定——
   version bump 语义,bookkeeping 写不触发）；
3. KB 开关开启。

**防抖**：用户可能连续保存。复用 asynq `Unique` 选项实现轻量防抖：
任务以 `wiki_page_id` 为唯一键、`ProcessIn(2min)` 延迟投递。窗口内的后续编辑因
Unique 冲突不再入队,窗口结束后任务执行时读取的是**最新**页面内容——天然合并。
不引入额外的防抖表。

`pipeline / agent / revert` 三种 EditSource 一律不触发（环路防断第一道闸）。
revert 不触发的理由：回滚目标版本若此前抽取过,claims 已存在;若担心漂移,
交给 C6 巡检按 extractor_version/时间戳兜底,不在写路径上加复杂度。

### 6.3 生命周期联动（清理）

| 事件 | 挂钩点 | 动作 |
|------|--------|------|
| 文档删除 | `knowledge_delete.go` 现有清理链 | `DeleteByKnowledge` |
| chunk 禁用/删除 | `chunk.go` 更新路径 | `DeleteBySource(chunk, id)`（禁用即出索引,与检索语义一致） |
| chunk 用户编辑（ContentRevision++） | 同上 | `DeleteBySource` + 重新入队抽取（reason=manual） |

## 7. 冲突粗筛改造（knowledge_conflict.go）

`coarseFilterBySearch` 重构为双通道候选生成,**函数签名与下游 fineAdjudicate 协议不变**
（conflictPair 结构不动,新增可选字段）：

```go
type conflictPair struct {
    NewChunk      *types.Chunk
    ExistingChunk *types.Chunk
    NewTitle      string
    ExistingTitle string
    ConflictType  string
    Reason        string
    // C1 新增（可选,为 C2/C4 铺路;本期仅透传）
    ClaimKeyHit   string   // 声明键命中时的 claim_key,"" 表示相似度兜底通道
    NewClaimIDs   []string // 命中配对的新方 claim id
    ExistClaimIDs []string
}
```

**主通道（声明键配对）**：

```
1. 取新 knowledge 全部 claims（本次抽取产物）
2. ListByKeys(kb, distinct claim_keys, exclude 自身 source)
3. 命中的对端 claims 按 source 反查 chunk / wiki 页面 → 构造 conflictPair
4. 同 source 去重：同一 (新chunk, 旧source) 只保留一对（多键命中合并,
   claim id 列表并联,LLM 裁决时上下文更完整）
```

对端为 wiki 页的配对：本期 ExistingChunk 以"伪 chunk"承载页面内容片段
（span 邻域 ±500 rune）,`KnowledgeID` 置 `wiki:<page_id>` 前缀标识。
knowledge_conflicts 表不改列（C4 才引入正式的 wiki 关联建模）,
该前缀行为在 C4 迁移中转正。**首期 wiki 对端配对仅落库为 pending,
不参与 chunk 禁用副作用**（Resolve 侧对 `wiki:` 前缀跳过禁用,仅记录裁决）。

**兜底通道**：现有 HybridSearch 路径原样保留,两处收紧：
- 仅对**未产出任何 claim** 的新 chunk 启用（有 claims 的 chunk 走主通道已覆盖,
  避免重复候选）;
- claims 完全缺失（抽取失败/开关刚开启存量未回填）时整体回退 V1 行为。

**预期效果**（验收口径）：`testdata/wiki_test/` 预埋矛盾对经主通道全部召回;
候选对总量相对 V1 下降（配对更准）,进入 LLM 的对数下降幅度在 C1 阶段即可观测。

## 12. 边界情况与已知限制

| 情况 | 处理 |
|------|------|
| 表格/图片型 chunk | 表格文本正常抽取;图片 OCR 内容视同文本;空文本 chunk 跳过 |
| FAQ 型 KB | 首期不启用(FAQConfig 存在时开关置灰)——问答对的声明化语义另议 |
| 超长 wiki 页（>50k rune） | 分窗抽取（窗口 8k、重叠 500）,span 按窗偏移还原 |
| 多语言混排 | 键规范化不做翻译归一,中英同义主体不会合并（漏配交兜底通道;C2 后评估同义词表） |
| 代词主体（"该产品上限为…"） | prompt 要求自含主体;LLM 未消解时该声明丢弃（计数告警） |
| 同 chunk 内自相矛盾 | 正常产出两条同键异值 claims;配对阶段排除同 source 自比,留给 C6 巡检报"源内矛盾" |
| claims 表膨胀 | 上限估算：10 万 chunk × 30 claims ≈ 300 万行,单 KB 索引查询走 (kb, claim_key) 复合索引;超限风险在 C6 分区/归档议题中处理 |

```
[system]
你是知识库声明抽取器。从给定文本中抽取"原子事实声明",每条为一个四元组:
主体(subject)、属性(predicate)、取值(value)、限定词(qualifiers)。
规则:
1. 只抽客观事实断言(数值、日期、状态、归属、定义);不抽主观评价、操作步骤、示例、假设;

4. qualifiers 尽量填 time(时效)/scope(适用范围)/unit(单位)/condition(前提条件),没有则省略;

[user]
以下是同一文档的 {n} 个片段,chunk_index 从 0 开始:
--- 片段 0 ---
{content_0}
--- 片段 1 ---
{content_1}
...
```
