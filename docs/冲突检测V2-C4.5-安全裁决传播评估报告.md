## 1. 目标与范围

C4-Lite 已将多条 raw `knowledge_conflicts` 聚合为一个 `DisputedFact`，但原有 Resolve
仍需人工逐 raw pair 操作。C4.5 的最小目标是：

```text
一次 DisputedFact 安全裁决
→ 该 cluster 的全部 pending raw members 一致更新
→ DisputedFact rebuild 为 resolved
→ 不禁用任意 chunk
```

当前仅实现不需要全局胜方定义的安全子集：

```text
resolved_keep_both
resolved_not_conflict
```

明确不实现：

```text
resolved_newer_wins
resolved_older_wins
cluster 级 winner selection
wiki dispute block 写回
agent 叙事改写
```

cluster 内 member 的 A/B 方向可不同；在 C3 没有定义文档版本、时间和来源权威性之前，
逐 raw member 套用“新/旧胜出”会错误禁用来源。

## 2. 实现

### 2.1 API

```text
POST /api/v1/knowledge-bases/:id/conflicts/clusters/resolve
```

请求：

```json
{
  "disputed_fact_id": "<cluster id>",
  "resolution": "resolved_keep_both | resolved_not_conflict",
  "note": "optional audit note"
}
```

接口由既有 KB write 权限保护。服务验证 cluster 属于当前 tenant/KB，且只更新该 cluster
的 pending raw rows。

### 2.2 原子更新与返回值

`KnowledgeConflictRepository.ResolvePendingByClusterID` 在一个 repository transaction 中：

```text
定位 tenant + KB + cluster_id + pending 的 member rows
→ 批量更新 status / resolved_by / resolved_at / resolution_note
→ 返回被更新的具体 member rows
```

服务随后在同一进程 cluster lock 下 rebuild，返回：

```text
updated_conflict_ids
updated_conflict_count
clear_penalty_chunk_ids
rebuild
```

`clear_penalty_chunk_ids` 是所有已更新 member 的去重 chunk ID 集；因为 pending status
消失，现有 penalty 查询自然不再将这些 chunk 视为待裁决冲突。

### 2.3 状态列修复

真实运行发现历史 M3 schema 的：

```text
knowledge_conflicts.status VARCHAR(20)
```

无法保存 21 字符的 `resolved_not_conflict`。Migration 修复为：

```text
PostgreSQL 000089: status VARCHAR(32)
SQLite     000010: version-alignment no-op（SQLite TEXT 无长度限制）
```

实验检查和 resolution script 均会预先检查该宽度，避免以不透明 HTTP 400 暴露。

## 3. 真实运行结果

两次均使用 C4 exact 三值 cluster：

```text
100 元 / 150 元 / 200 元
3 raw conflicts
1 DisputedFact
3 sources
```

### 3.1 `resolved_keep_both`

```text
source run: 20260901T023101Z-c4_cluster_triplet-c2-batch-cc9423d4
DisputedFact: 33ebca6d-1d58-442c-8142-d86934eb0b1b
```

脚本验证：

```text
updated raw conflicts: 3
3 / 3 members → resolved_keep_both
所有 member cluster_id 相同
resolved_by / resolution_note 一致
无 chunk 禁用
DisputedFact rebuild 后 pending_conflict_count = 0
```

### 3.2 `resolved_not_conflict`

```text
source run: 20260901T032922Z-c4_cluster_triplet-c2-batch-cc9423d4
DisputedFact: bf212e17-e2ee-4472-957a-f234d1999e8b
```

脚本/API 返回：

```text
updated_conflict_count: 3
updated_conflict_ids: 3
clear_penalty_chunk_ids: 3
```

最终数据库验证：

```text
3 / 3 members → resolved_not_conflict
DisputedFact.status: resolved
DisputedFact.conflict_count: 3
DisputedFact.pending_conflict_count: 0
DisputedFact.source_count: 3
candidate_values: [100 元, 150 元, 200 元]
```

这次运行同时验证 migration `000089` 已生效。

## 4. 可复现实验命令

```bash
# 先创建一个有一个 pending cluster 的临时 C4 run
make experiment-c4
RUN="$(ls -td experiments/runs/*-c4_cluster_triplet-c2-batch-* | head -1)"

# 安全保留多来源
make experiment-c4-resolve RUN="$RUN"

# 在另一份 fresh run 上验证 false-positive 关闭路径
make experiment-c4-resolve \
  RUN=experiments/runs/<fresh-c4-run> \
  RESOLUTION=resolved_not_conflict
```

脚本会写入：

```text
<run>/cluster_resolution.json
```

并在成功退出前验证：

```text
API updated IDs == 调用前全部 pending member IDs
被处理 member 的 status == 请求的 resolution
DisputedFact.status == resolved
DisputedFact.pending_conflict_count == 0
```
